# 09 · 可观测性：日志、请求 ID 与审计留痕

本文描述系统如何记录自身行为：结构化日志的字段与落盘方式、`request_id` 如何贯穿请求、
任务执行留痕了什么、故障切换事件如何被记录与展示，以及**哪些东西故意不写进日志**。
结论均来自源码，行号以当前代码为准。

## 1. 结构化 JSON 日志

## 2. `request_id` 如何贯穿请求与日志

### 2.1 生成与绑定

`backend/app/api/deps.py:19-23`：

```python
async def bind_request_id(request: Request) -> str:
    rid = request.headers.get("X-Request-ID") or new_request_id()
    request_id_var.set(rid)
    request.state.request_id = rid
    return rid
```

| 行为 | 说明 |
|---|---|
| 复用外部 ID | 请求头带 `X-Request-ID` 时沿用，便于跨系统串联 |
| 否则新建 | `new_request_id()` = `uuid.uuid4().hex[:16]`（`logging.py:26-27`） |
| 写入 ContextVar | 后续同一协程内所有日志自动带上 `request_id`（`logging.py:49`） |
| 写入 `request.state` | 供处理器内部使用 |

依赖别名：`RequestIdDep`（`deps.py:56`）。CORS 已在 `allow_headers` 中放行 `X-Request-ID`
与 `X-Admin-Token`（`main.py:123`）。

### 2.2 挂载了 `RequestIdDep` 的接口

| 接口 | 位置 |
|---|---|
| `GET /api/v1/market/overview` | `api/market.py:22` |
| `POST /api/v1/portfolio/plans` | `api/portfolio.py:22` |
| `POST /api/v1/research/backtest` | `api/research.py:20` |
| `POST /api/v1/research/replay` | `api/research.py:40` |
| `GET /api/v1/research/...` | `api/research.py:48` |
| `POST /api/v1/assistant/ask` | `api/assistant.py:192` |

**注意（如实说明）**：

1. 挂载的目的是**绑定**（副作用），处理器里拿到的 `rid` 变量本身**没有被使用** —— 既没有打印，也没有拼进返回值；
2. 响应头**没有回写** `X-Request-ID`。`main.py:126-133` 的 `security_headers` 中间件只写了
   `X-Content-Type-Options` / `X-Frame-Options` / `Referrer-Policy` / `Cache-Control`；
3. 因此客户端只能通过**服务端日志**按 `request_id` 检索，无法从 HTTP 响应里拿到它；
4. 未挂载该依赖的接口（如 `/system/*` 系列）在请求上下文内也会因中间件缺失而沿用默认值 `"-"`。

## 3. 任务执行留痕：`system_jobs` 表

模型：`backend/app/db/models.py:629-639`（类名 `SystemJob`）。

| 字段 | 语义 |
|---|---|
| `job_name` | 任务名（index） |
| `status` | `success / failed / running / skipped` |
| `started_at` / `finished_at` | 起止时间 |
| `duration_ms` | 耗时毫秒 |
| `rows_affected` | 影响行数 |
| `provider` | 实际使用的数据源 |
| `message` | 结果摘要或错误原因（**截断 500 字符**） |

写入逻辑在采集器基类：`backend/app/collectors/base.py`。

| 函数 | 行号 | 行为 |
|---|---|---|
| `_job_start` | 120-127 | 插入 `status="running"` + `started_at`，`refresh` 后返回 id |
| `_job_finish` | 129-142 | 回填 `status / finished_at / duration_ms / rows_affected / message[:500] / provider` |
| `run()` | 145-156 | 统一入口：成功 → `success`；异常 → 记 `collector.failed` 后写 `failed`，并返回 `{"ok": False, ...}` 而**不向外抛** |

`run()` 的注释（`base.py:153`）说明这是刻意的：「单点失败不应击穿调度器」。

调度器侧另有一层运行时状态（`scheduler/manager.py:135-153`）：

| 项 | 说明 |
|---|---|
| `scheduler.task_done` | 记录 `job / status / ok` |
| `scheduler.task_error` | 记录异常（截断 300 字符） |
| `_jobs[job_id]` 内存态 | `last_run` / `last_status`，供 `GET /api/v1/system/jobs` 展示 |

需要区分：`system_jobs` 表是**持久化**留痕（每次采集一行），调度器的 `_jobs` 是**进程内**状态（重启即失）。

## 4. 故障切换事件：如何被记录与展示

### 4.1 事件产生的时机

`backend/app/providers/router.py:158-165`：只有当**实际使用了备用源**（`idx > 0`）时才登记切换：

```python
if used_fallback:
    await self.health.record_failover(
        category=..., from_provider=primary_name,
        to_provider=provider.name, reason=first_failure_type or attempt.failure_type or "unknown")
```

同时 `RoutedResult` 会携带 `used_fallback` / `failover_reason` / `failover_time` / `attempts`
供前端展示（`providers/types.py:178-205` 的 `to_source_block`）。

### 4.2 事件被写到哪里（关键事实）

`backend/app/providers/health.py:180-199` 的 `record_failover` 只做两件事：

| 动作 | 行号 | 结果 |
|---|---|---|
| 计数器 `rec.failover_count_today += 1` | 183 | 内存 |
| 追加到 `self._failover_events`（`deque(maxlen=500)`，声明于 `health.py:83`） | 184-192 | **内存**，进程重启即失 |
| `logger.event("provider.failover", ...)` | 193-198 | 日志 |

它**没有**向数据库表 `provider_failover_events` 写任何一行。

### 4.3 展示读的是哪里

| 出口 | 位置 | 数据源 |
|---|---|---|
| `GET /api/v1/system/providers/failovers` | `api/system.py:88-90` → `HealthService.failover_events` | **数据库表** `provider_failover_events`（`services/health_service.py:90-106`） |
| `GET /api/v1/system/failover-events`（别名） | `api/system.py:192-194` | 同上 |
| `ProviderHealth.failover_events()`（内存版） | `providers/health.py:328-338` | 内存 deque，**没有任何 API 调用它** |

### 4.4 结论：故障切换的持久化留痕目前不生效

| 事实 | 依据 |
|---|---|
| 表 `provider_failover_events` 已建（`models.py:125-135`），字段含 `category / from_provider / to_provider / reason / resolved / resolved_at / occurred_at` | `models.py:125-135` |
| 全仓库对 `ProviderFailoverEvent` 的引用只有三处：模型定义、`ALL_TABLES`、以及 `HealthService` 的**查询** | `models.py:125/669`、`health_service.py:13/94` |
| 没有任何代码向该表 `add` | 同上 |

因此 `/api/v1/system/providers/failovers` 与 `/failover-events` 在当前代码中**恒返回空列表**。
切换事件目前只能通过 `provider.failover` 日志与响应体里的 `source.attempts` / `used_fallback` 观察到。

## 6. 故意不写进日志 / 不暴露的内容

| 类别 | 机制 | 位置 |
|---|---|---|
| 日志字段脱敏 | `scrub()` 对键名做小写包含匹配，命中即替换为 `***REDACTED***` | `logging.py:30-39` |
| 脱敏关键词表 | `api_key, apikey, token, secret, password, authorization, access_token, refresh_token, key, passwd` | `logging.py:20-23` |
| 数据库口令 | `redact_url()` 把 URL 中的 password 替换为 `***`，`db.engine_ready` 只打脱敏后 URL | `db/base.py:106-116`、83 |
| 接口不返回密钥 | `GET /api/v1/system/info` 只回显非敏感项，并附 `note` 说明 | `api/system.py:56-69` |
| LLM Key | 仅用于 `Authorization` 请求头，不进 `extra_fields` | `api/assistant.py:177` |
| 异常摘要截断 | 错误原因统一截断 200/300 字符，避免超长堆栈污染日志 | `base.py:154-155`、`router.py:79` 等 |
| 备份包内的 `.env` | 备份时打包但提示「含密钥，请妥善保管」，不打印内容 | `scripts/backup.py:231` |

`scrub` 只作用于 `event()` 传入的 `extra_fields`；`msg` 本身不脱敏，
因此**调用方仍需自行避免把密钥拼进 `msg`**。

## 7. 排障时的推荐检索路径

| 想查什么 | 看哪里 |
|---|---|
| 某次请求发生了什么 | 按 `request_id` 过滤 `logs/platform.log` |
| 某个采集任务是否跑过、写了几行 | `system_jobs` 表（`job_name` + `status` + `rows_affected`） |
| 历史回填中断在哪 | `sync_checkpoints.cursor_date` / `last_error` + 事件 `collect.backfill_interrupted` |
| 哪些窗口确实没数据 | 事件 `collect.backfill_no_coverage` + 断点 `extra.uncovered_windows` |
| 是否发生过主备切换 | 事件 `provider.failover`；响应体 `source.used_fallback` / `attempts`（**持久化表暂不可用**） |
| Provider 是否被自动停用 | 事件 `provider.auto_disable` |
| 写入时被丢弃了哪些字段 | 事件 `db.upsert_dropped_columns` / `db.upsert_conflict_key_missing` |
