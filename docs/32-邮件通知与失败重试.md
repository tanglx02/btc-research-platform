# 32 邮件通知与失败重试

一句话定位：提醒一旦触发就**不会因为发信失败而丢失**，先落库再发送，失败自动补发，连续失败会明确告警。

## 代码位置

| 文件 | 职责 |
| --- | --- |
| `backend/app/alerts/notifier.py` | `NotificationProvider` 协议、`EmailProvider`（SMTP）、配置加载与诊断 |
| `backend/app/alerts/pipeline.py` | `dispatch_pending()` 补发轮询、`_send_event()` 发信、熔断、日志 |
| `backend/app/alerts/templates.py` | 邮件主题与正文（纯文本 + HTML 双版本） |
| `backend/app/api/alerts.py` | SMTP 配置、测试、诊断、摘要接口 |

## 通知渠道抽象

第一阶段只实现 SMTP，但接口按多渠道设计，后续接 Telegram / Discord / Web Push / Webhook 不需要改业务代码：

```python
class NotificationProvider(Protocol):
    def available(self) -> tuple[bool, str]: ...          # (可用?, 原因)
    async def send(self, message: OutgoingMessage) -> NotifyResult: ...
```

`build_provider(channel_type, overrides)` 按渠道类型构造实现；`supported_channels()` 供前端列出可选项。

## SMTP 配置

配置项（**不写死在代码里**，页面配置优先于环境变量）：

| 字段 | 说明 |
| --- | --- |
| Server | SMTP 服务器地址 |
| Port | 端口（SSL 465 / STARTTLS 587 / 明文 25） |
| Encryption | `ssl` / `starttls` / `none` |
| Username | 登录名 |
| Password | 密码或授权码 |
| From / From Name | 发件地址与显示名 |
| To | 收件人，多个逗号分隔 |
| Timeout | 单次超时秒数 |

`SmtpConfig.describe()` 输出配置摘要时**永不包含密码**。

## 发送流程

```
事件落库（notification_status=PENDING）
        │
        ▼
  dispatch_pending()  ──取 PENDING/FAILED 且未超轮次的事件──┐
        │                                                   │
        ▼                                                   │
  _send_event() ── 渠道循环 ── 最多 MAX_SEND_ATTEMPTS 次尝试 ─┤
        │                                                   │
        ├─ 成功 → SENT，记录 email_sent_at / email_message_id
        └─ 失败 → FAILED，记录 error_message，等待下一轮补发 ──┘
```

### 关键设计：inline attempts 与补发轮次分离

| 概念 | 含义 | 存储 |
| --- | --- | --- |
| `attempts` | **同一时刻**内的连续尝试次数（应对瞬时抖动） | `alert_notification_logs` 逐条 |
| `retry_count` | **补发轮次**（每一轮 `dispatch_pending` 加一） | `alert_events.retry_count` |

早期实现里，一次瞬时网络故障就把补发预算耗尽了。现在发送失败**不再**累加 `retry_count`，而是由 `dispatch_pending` 每轮统一 +1。这样一次抖动不会吃掉后续补发机会。

## 状态与重试

| 状态 | 含义 |
| --- | --- |
| `PENDING` | 已触发，尚未成功发出 |
| `SENDING` | 正在发送 |
| `SENT` | 发送成功 |
| `FAILED` | 发送失败，等待补发 |
| `SKIPPED` | 没有可用渠道（如未配置 SMTP）——**仍然保留事件**，不算丢失 |

- 单次发送最多 `MAX_SEND_ATTEMPTS = 3` 次尝试。
- 致命错误（如认证失败 535）**短路**，不做无意义重试，直接记录原因。
- 非致命错误（超时、连接重置）走重试。

## 熔断

连续失败达到 `CHANNEL_FAILURE_THRESHOLD = 5` 次后，该渠道进入 `CHANNEL_COOLDOWN_SECONDS = 1800`（30 分钟）冷却，避免持续无效发信。

熔断期间：事件仍在正常落库，只是暂缓发送；冷却结束后自动恢复尝试。

## 失败可见性

- 每次尝试都写 `alert_notification_logs`（含 SMTP 响应原文与错误信息）。
- 连续失败会在**日志**与**系统通知**中明确提示，不会静默吞掉。
- 页面上可以直接看到：事件的通知状态、失败原因、重试次数、每一条发信日志。

## 邮件内容

邮件必须**专业但通俗**，包含：

| 内容 | 说明 |
| --- | --- |
| 触发时间 | 精确到秒，含时区 |
| 规则名称与自然语言描述 | 如「BTC 当前价格 大于 100000 USD」 |
| 实际值与阈值 | 让用户看到「差多少」 |
| 为什么触发 | 逐条件的判定依据 |
| 关键指标快照 | 回撤、MVRV、分位、风险等级、市场阶段等 |
| 数据状态 | 数据质量等级、是否降级 |
| 数据来源 | 实际使用的 Provider 与是否 fallback |

同时提供**纯文本**与**HTML**两个版本，纯文本版保证在任何客户端都能读。

## 提醒等级

`INFO` / `WARNING` / `HIGH` / `CRITICAL`，影响主题前缀与正文配色。

## 摘要邮件

- **每日摘要**：`ALERT_DIGEST_DAILY_HOUR`（默认 9 点）
- **每周摘要**：`ALERT_DIGEST_WEEKLY_WEEKDAY` + `ALERT_DIGEST_WEEKLY_HOUR`
- 页面提供「预览」接口，先看内容再决定发不发。

## 测试与诊断

| 接口 | 作用 |
| --- | --- |
| `POST /alerts/notify/smtp/test` | 发送测试邮件，返回成功/失败、错误原因、SMTP 响应原文 |
| `POST /alerts/notify/smtp/diagnose` | 只做连通性与认证检查，不真发信 |
| `POST /alerts/events/{id}/resend` | 对某条历史事件手动重发 |
| `POST /alerts/rules/{id}/test` | 用当前数据判断规则是否成立，**不落库、不发信** |

## 邮件失败不丢提醒的保证

1. 触发时**先写事件**（含完整指标快照），再尝试发送。
2. 发送失败只更新 `notification_status`，事件本身不动。
3. `alert_retry` 任务定期扫 PENDING/FAILED 事件补发。
4. 用户在页面上随时能看到「哪些提醒还没发出去、为什么」。
