# 31 智能监测与条件预警

一句话定位：把「什么数据、什么条件、什么时候提醒」做成一个通用的条件规则引擎，用户自己组合条件，新增指标不需要改通知系统。

## 代码位置

| 文件 | 职责 |
| --- | --- |
| `backend/app/alerts/catalog.py` | 指标目录 `CATALOG`、取值器注册表 `_RESOLVERS`、求值上下文 `MetricContext` |
| `backend/app/alerts/resolvers.py` | 62 个指标的取值实现，全部只读已有数据层 |
| `backend/app/alerts/engine.py` | 规则求值器 `RuleEngine`：条件、分组、时间修饰、跨越判定、质量门槛 |

## 指标目录（62 个）

指标与取值器**分离注册**：`catalog.register(spec)` 只登记定义，`catalog.resolver(code)` 登记取值函数。这样做的直接好处是——新增一个可监测指标只需在 `resolvers.py` 里加一个函数并注册，规则引擎、校验器、前端下拉菜单、邮件取值**全部自动生效**，不需要改通知系统。

## 组合与时间维度

- **组合**：`ConditionGroup` 递归嵌套，支持 `AND` / `OR` / `NOT`，任意深度，可实现 `(A AND B) OR (C AND D AND E)`。
- **持续时间** `duration_seconds`：条件需持续成立 5m/15m/1h/4h/1d/自定义秒数。
- **连续次数** `consecutive_count`：需连续 N 次评估都满足。
- 时间维度与运算符**正交**：任意运算符都能叠加持续/连续约束。

## 状态机

```
NORMAL ──成立──> TRIGGERED ──冷却期──> COOLDOWN ──条件不再成立──> RECOVERED
   ^                                                                │
   └──────────────── 再次成立（跳过冷却，重新触发）──────────────────┘
```

- 冷却期内**不重复发信**，但仍在记录状态。
- 条件恢复且规则开启 `notify_on_recover` 时，发一封「已恢复」邮件。
- 恢复后条件再次成立，可以**重新触发**并再次通知。

## 数据质量门槛

质量等级序：`ANY < MISSING < STALE < SINGLE_SOURCE < VERIFIED < CROSS_VERIFIED`。

规则可设置：

| 字段 | 作用 | 默认值 |
| --- | --- | --- |
| `min_quality` | 低于该等级的数据不参与判定 | `SINGLE_SOURCE` |
| `require_fresh` | 数据必须在有效时效内，且不得是 STALE 降级数据 | `True` |
| `require_multi_source` | 必须 ≥2 个独立数据源交叉确认 | `False` |

不满足门槛时**不触发关键提醒**，不拿过期或单源数据去打扰用户。

**为什么 `min_quality` 默认是 `SINGLE_SOURCE` 而不是 `VERIFIED`**：
`VERIFIED` 要求同一时刻有 2 个以上数据源同时应答，真实网络里并不总能满足（演练中 14 个类别全部只达到 SINGLE_SOURCE）。
若默认 `VERIFIED`，用户按默认新建的第一条规则会「条件成立却永远收不到邮件」。
单源真实数据本身就是可信数据——来源与质量都会被如实写进事件、并在邮件里显示，不构成隐瞒。
「重要规则要求 ≥2 源确认」留给 `require_multi_source` / `min_quality=VERIFIED`，由用户按需开启。

**真正必须默认守住的是新鲜度**：`require_fresh=True` 会拦下所有 STALE 降级数据。
这才是「不能用过期数据触发关键提醒」这条硬约束的落点——演练场景 C（全源失效）正是靠它把 `would_notify` 压成 `False`。

## 与调度器的关系

预警引擎复用现有 Scheduler，**不另建定时系统**：

| 任务 | 默认周期 | 作用 |
| --- | --- | --- |
| `alert_engine` | 60 秒 | 一次取数统一评估所有到期规则 |
| `alert_retry` | 300 秒 | 补发失败的通知 |
| `alert_digest` | 900 秒 | 检查并发送每日/每周摘要 |

## 性能约束

- 一个评估周期内，**所有规则共享一次取数**（`build_context` 只调用一次），不给每条规则单独请求数据源。
- 同一指标在一次求值中只解析一次（`MetricContext._cache`）。
- 单周期最多处理 `ALERT_MAX_RULES_PER_CYCLE`（默认 500）条规则。

## 安全校验（`rules.py`）

规则保存前必须通过校验，覆盖：

- 指标不存在 / 指标无取值实现
- 缺少必要阈值、区间缺上界、变化率缺窗口、交叉缺比较对象
- 窗口或时间范围非法
- 价格类指标阈值必须为正（资金流类允许为负）
- AND 分组内自相矛盾（下界 ≥ 上界）
- 重复条件
- 检测频率过高（最小 30 秒）、冷却过短（最小 60 秒）
- 条件数量超限（最多 50 个）
- 无条件规则

校验失败返回**具体到第几个条件、哪个字段**的中文原因。
