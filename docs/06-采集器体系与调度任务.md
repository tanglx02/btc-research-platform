# 06 采集器体系与调度任务

一句话定位：数据怎么进来（回填 / 增量 / 补洞），以及**只有一个调度器**统管全部 15 个任务。

## 代码位置

| 文件 | 职责 |
| --- | --- |
| `backend/app/collectors/base.py` | 采集器基类 |
| `backend/app/collectors/market_collector.py` | 行情采集 |
| `backend/app/collectors/data_collectors.py` | 其他类别采集 |
| `backend/app/scheduler/manager.py` | **唯一**调度器 `SchedulerManager` |
| `backend/app/db/repo.py` | Raw + Normalized 双写、幂等 |

## 采集三步走

| 阶段 | 说明 |
| --- | --- |
| **历史回填** | 首次启动按 `BACKFILL_START_DATE`（默认 2013-01-01）分批拉取，`BACKFILL_BATCH_DAYS=500` 控制每批跨度 |
| **增量同步** | 按各任务周期拉取最新数据，`sync_checkpoints` 记录进度 |
| **缺口补洞** | `gap_repair` 任务定期扫描断点并补齐 |

断点续传与补洞详见 `07-断点续传与缺口补洞.md`。

## 为什么预警任务优先级更低

预警是**消费方**，不是**生产方**：

- 采集任务先跑，把数据放进库里，预警才有得读。
- 优先级设低可以避免与采集争抢 Provider 配额。
- 预警**一个周期只取数一次**，全部到期规则共享同一份上下文，不会 500 条规则产生 500 次请求。

## 频率与限流

- 每个任务的周期都有下限（`max(N, 配置值)`），防止误配成每秒调用。
- 实时价格最快 10 秒；链上/宏观按数据源更新频率设到小时级，不做无意义的「实时」。
- Provider 侧还有 `RATE_LIMITED` 状态与限流保护。
- ETF 原先复用 `JOB_MACRO_SECONDS`，后改为独立配置项以便单独调频。

## 调度器唯一性

**全项目只有一个 `SchedulerManager`。** 智能监测模块没有新建调度器，只是在 `_build_jobs()` 列表里追加了 3 项，并新增 `_alert_cycle` / `_alert_retry` / `_alert_digest` / `_digest_due` 四个方法。

`scheduler/manager.py` 中的 `_digest_sent` 用于保证摘要「到点只发一次」，避免重复邮件。
