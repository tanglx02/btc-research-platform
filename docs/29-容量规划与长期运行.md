# 29 · 容量规划与长期运行

调度周期、写入量、留存策略与缓存策略的真实实现，以及当前尚未接线的部分。

## 调度任务与周期

`SchedulerManager._build_jobs()` 定义 11 个任务，均为 `IntervalTrigger(seconds=...)`；环境变量可覆盖，且有**最小下限**（`max(下限, 配置值)`）：

| 优先级 | job_id | 环境变量（默认秒） | 下限 | 说明 |
| --- | --- | --- | --- | --- |
| 1 | `market_tick` | `JOB_MARKET_TICK_SECONDS`（30） | 10 | BTC 实时价格（多源 + 交叉验证） |
| 2 | `market_1h` | `JOB_MARKET_1H_SECONDS`（300） | 60 | 1 小时 K 线增量同步 |
| 3 | `market_1d` | `JOB_MARKET_1D_SECONDS`（1800） | 300 | 日线增量同步 |
| 4 | `derivatives` | `JOB_DERIVATIVES_SECONDS`（300） | 60 | 资金费率 / 持仓量 |
| 5 | `onchain` | `JOB_ONCHAIN_SECONDS`（3600） | 300 | 链上基础数据 |
| 6 | `sentiment` | `JOB_SENTIMENT_SECONDS`（3600） | 600 | 恐慌贪婪指数 |
| 7 | `macro` | `JOB_MACRO_SECONDS`（21600） | 1800 | 宏观序列 |
| 8 | `etf` | `JOB_MACRO_SECONDS`（21600） | 3600 | ETF 资金流（未配置 Key 时自动跳过） |
| 9 | `quality` | `JOB_QUALITY_SECONDS`（3600） | 600 | 数据质量扫描 |
| 10 | `gap_repair` | `JOB_QUALITY_SECONDS`（3600） | 1800 | 历史缺口自动补洞 |
| 11 | `health_probe` | `JOB_HEALTH_SECONDS`（120） | 60 | 汇总运行时健康（不打外部 API） |

调度器行为：

- 使用 `AsyncIOScheduler(timezone="UTC")`，每个任务 `max_instances=1`、`coalesce=True`、`misfire_grace_time=120`、`replace_existing=True`；
- 启动条件：`SCHEDULER_ENABLED=true` 且 `APP_ENV != "test"`（在 `main.py` 的 lifespan 中启动/停止）；
- 任务被 `_safe_run()` 包裹：异常只记 `scheduler.task_error` 并置 `last_status=failed`，不会击穿调度器；
- 手动执行：`POST /api/v1/system/jobs/{job_id}/run`（Admin）或运维菜单；失败返回 `{"ok": false, "error": ...}`，不存在的 id 返回「任务不存在」；
- 回填：`SchedulerManager.run_backfill(start_date, reset)` → `MarketCollector(interval="1d").run(mode="backfill", ...)`。

## 写入量与增长估算

按默认周期估算（单 symbol=BTC）：

| 数据 | 频率 | 行数/天 |
| --- | --- | --- |
| `MarketPrice`（tick） | 每 30 秒 | 约 2880 |
| `RawMarketData`（tick 留档） | 每 30 秒 | 约 2880 |
| `Candle` 1h | 每 300 秒增量（重叠补最近 3 根） | 幂等 upsert，稳态约 24 根/天 |
| `Candle` 1d | 每 1800 秒增量 | 幂等 upsert，稳态约 1 根/天 |

历史回填一次性的量级：`BACKFILL_START_DATE=2013-01-01` 起，日线约 5000 根（按 `BACKFILL_BATCH_DAYS=500` 分批，中断后从 checkpoint 续传）。

写入实现要点：

- `upsert_candles` / `upsert_rows` 按 `CHUNK=500` 分块，用 `on_conflict_do_update`，冲突列必须与模型 `UniqueConstraint` 一致（如 `symbol,interval,ts,source_id`），重复运行不会产生新行；
- 模型里不存在的键会被逐行剔除并记 `db.upsert_dropped_columns`，不会整批失败；
- `insert_raw()` 每次成功取数都留档原始响应，`payload` 截断到 200000 字符，写入失败只记日志不中断业务。

## 数据留存策略

- 配置：`RAW_RETENTION_DAYS = 3650`（10 年）；
- 实现：`repo.purge_old_raw(session, days)` 按 `RawMarketData.fetch_time < now - days` 删除并返回行数；
- **实际接线情况：代码中未找到 `purge_old_raw` 的调用方，`RAW_RETENTION_DAYS` 也只出现在 `config.py` 的定义处**。也就是说，原始留档表当前只增不减，需要人工清理或自行接入调度。

其它存储注意点：SQLite 默认开启 WAL（`data/btc.db-wal`、`-shm`），备份必须三件套一起复制（见「25 · 更新回滚与备份恢复」）；PostgreSQL 可叠加 TimescaleDB（`enable_timescaledb()`）。

## 缓存策略

| 项 | 实现 |
| --- | --- |
| 后端选择 | 配置了 `REDIS_URL` 且能连通 → `RedisCache`；否则（含 Redis 不可用）自动降级 `MemoryCache`，并记 `cache.redis_unavailable` |
| TTL | `CACHE_TTL_SECONDS`（默认 60 秒） |
| 容量 | `CACHE_MAX_ENTRIES`（默认 5000），写满时先清过期、再按写入顺序淘汰 |
| Key | `make_key(prefix, *parts)` = `prefix:` + 原始串的 md5 前 12 位 |
| 失效 | `invalidate_prefix(prefix)` 仅对 `MemoryCache` 生效（Redis 分支为空实现） |
| 生命周期 | `get_cache()` 进程内单例；进程重启即失效 |

按设计约束（模块注释），缓存不得成为唯一数据源，数据库才是长期真相来源。

## 长期运行建议（当前需人工执行的部分）

| 项目 | 建议做法 |
| --- | --- |
| 原始留档清理 | 自行在维护窗口执行 `purge_old_raw`（暂无 CLI），或增加调用它的调度任务 |
| SQLite 维护 | 定期 `VACUUM`、确认 WAL 正常 checkpoint；库文件增大后关注磁盘 |
| 备份轮转 | `backups/` 每次备份都整库打包，需自行保留 N 份并删除旧包 |
| 日志 | `logs/platform.log` 单文件 20 MB × 10 分片自动轮转；长期归档另做 |
| 监控 | 无内建告警，需外部定时拉取 `/api/v1/system/providers/dashboard` 与 `/system/jobs` |

## 已知局限 / 注意事项

- `etf` 任务复用 `JOB_MACRO_SECONDS`（没有独立的 `JOB_ETF_SECONDS`），无法单独调整 ETF 采集频率。
- `purge_old_raw` 与 `RAW_RETENTION_DAYS` 未接线，`RawMarketData` 会随 tick 频率持续增长（默认约 2880 行/天）。
- 缓存实例在 `MarketService` 中被创建（`self.cache = get_cache()`），但当前代码里未找到实际 `get/set` 调用点，即缓存层尚未在业务路径生效。
- `invalidate_prefix()` 在 Redis 后端下为空实现，按前缀失效不会生效。
- 健康状态与 failover 事件都在进程内存中，重启清零；多 worker 部署（`--workers > 1`）会导致调度任务各跑一份。
- 调度器没有持久化 jobstore，进程停机期间的采集不会补跑，只能靠 `gap_repair` 与 `incremental` 事后补齐。
