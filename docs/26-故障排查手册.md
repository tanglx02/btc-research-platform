## 日志结构与位置

`setup_logging()` 同时挂载 stdout 与 `RotatingFileHandler`（`LOG_DIR/platform.log`，单文件 20 MB、保留 10 个备份，UTF-8）。每条日志是单行 JSON：

```json
{"ts":"2026-09-27T02:00:00+00:00","level":"INFO","logger":"app.main","msg":"app.starting",
 "request_id":"a1b2c3d4e5f60718","provider":"binance","env":"development","version":"1.0.0"}
```

- 固定字段：`ts`、`level`、`logger`、`msg`、`request_id`、`provider`（来自 ContextVar，未设置时为 `-`）；
- `logger.event(msg, **fields)` 的字段并入 `extra_fields`，并先经 `scrub()`：键名包含 `api_key/apikey/token/secret/password/authorization/access_token/refresh_token/key/passwd` 的值替换为 `***REDACTED***`；
- 异常时附带 `exc` 字段；
- `httpx` 与 `apscheduler.executors.default` 被降噪到 WARNING。

常用排查命令（Windows 用 Git Bash 的 `grep`，或 `findstr`）：

```bash
grep '"level":"ERROR"' logs/platform.log | tail -50
grep 'provider.failure' logs/platform.log | tail -30
grep 'provider.failover' logs/platform.log | tail -30
grep '"request_id":"<从响应头或前端拿到的 ID>"' logs/platform.log
grep 'app.unhandled_error' logs/platform.log | tail -20
```

## Provider 故障类型 → 处置策略（`FAILURE_POLICY`）

| failure_type | 策略 | 运行时表现 |
| --- | --- | --- |
| `timeout` / `connect_error` / `dns_error` / `proxy_error` / `tls_error` | failover | 立即切下一个源 |
| `rate_limited` (429) | backoff | 降低频率+退避，必要时切换；健康状态置 RATE_LIMITED |
| `server_error` (5xx) | retry_failover | 重试后切换 |
| `forbidden` (403) | disable_temporary | `router` 直接把 `provider.enabled=False`，日志 `provider.auto_disable` |
| `auth_error` | alert_admin | 同上也会自动停用（密钥无效不无限重试） |
| `not_configured` | alert_admin | 显示「数据源未配置」，相关模块置不可用 |
| `data_format_error` | disable_temporary | 自动停用并记 `provider.auto_disable` |
| `data_quality_error` / `empty_data` / `stale_data` | failover | 拒绝脏数据并切换 |
| `unsupported_input` / `range_unsupported` | failover | **只切下一个源，不停用该 Provider** |
| `unknown` | failover | 兜底切换 |

状态机（`health.status_of()`）优先级：手动状态 > DISABLED > NOT_CONFIGURED > RATE_LIMITED > 连续失败 ≥ `FAILURE_THRESHOLD`(3) 映射为 `NETWORK_ERROR/AUTH_ERROR/DATA_ERROR/OFFLINE` > DEGRADED（有失败或延迟 ≥ `DEGRADED_LATENCY_MS`=2500）> SLOW（≥1500）> UNKNOWN > ONLINE。

熔断：`cooldown_remaining()` 在连续失败 ≥2 时生效，`base=max(15, DEFAULT_BACKOFF_MAX*2)`，`cooldown=min(300, base*2^min(f-2,4))`；熔断中的源会在 attempts 里以 `circuit_open` 留痕。恢复主源需同时满足：连续成功 ≥3、延迟 ≤2500 ms、距上次失败 ≥180 s、一致性 ≥0.9。

## 现象 → 原因 → 排查

| 现象 | 可能原因 | 排查命令 |
| --- | --- | --- |
| 顶栏显示「数据源不可用」、价格 `--` | 全部 Provider 失败且本地无历史价；`/market/price` 返回 `available=false` | `curl 127.0.0.1:8787/api/v1/market/price`；`python scripts/btcctl.py probe`；`grep provider.failure logs/platform.log \| tail` |
| 价格有值但标记 STALE / 徽章「过期数据」 | `AllProvidersFailedError` 后回落到 `latest_price()` 本地最近可信值 | `curl .../api/v1/market/price` 看 `stale` 与 `source.attempts`；`python scripts/btcctl.py health` |
| 某 Provider 长期 NOT_CONFIGURED | 缺少对应 API Key（`GLASSNODE/COINGLASS/FRED/CRYPTOQUANT/OPENAI`） | `curl .../api/v1/system/providers`；检查 `.env`；`curl .../api/v1/system/info` |
| Provider 突然消失/已停用 | 触发 `auth_error`/`forbidden`/`data_format_error` 自动停用 | `grep provider.auto_disable logs/platform.log`；`curl .../api/v1/system/providers/dashboard` |
| 短暂不可用后自动恢复慢 | 熔断 + 恢复条件（连续 3 次成功 / 180 s 冷却 / 一致性 ≥0.9） | `curl .../api/v1/system/providers/failovers?limit=100` |
| 价格旁显示「数据源冲突」 | 交叉验证偏差 > `CROSS_VALIDATION_TOLERANCE_PCT`(0.35%)，取中位数且置信度下调至 ≤0.55 | 页面展开交叉验证块；`grep provider.failover logs/platform.log` |
| 历史 K 线为空/覆盖区间过短 | 未执行回填或回填中断 | `python scripts/btcctl.py coverage --interval 1d`；`python scripts/btcctl.py quality --interval 1d`；`python scripts/btcctl.py backfill --start 2013-01-01` |
| 缺口未补齐 | `gap_repair` 任务间隔较长（≥1800 s）或源不支持该区间（`unsupported_input`） | `python scripts/btcctl.py gap-repair --interval 1d`；`curl .../api/v1/system/data-quality` |
| 启动失败：`RuntimeError 生产环境必须设置 SECRET_KEY/ADMIN_TOKEN` | `.env` 中仍为默认值 | 修改 `.env` 后重启；`python scripts/platformctl.py doctor` |
| `start` 报端口被占用 | 8787 已被占用 | `python scripts/platformctl.py status`；修改 `.env` 的 `PORT` 或停止占用进程 |
| 25 秒内端口未就绪 | 首次启动迁移/种子数据慢，或启动异常 | `tail -n 80 logs/platform.log`；`grep app.starting logs/platform.log` |
| 管理接口 401/403 | 生产环境：401 = `X-Admin-Token` 缺失或不等于 `ADMIN_TOKEN`；403 = 写操作缺头 | 带 `-H "X-Admin-Token:$ADMIN_TOKEN"` 重试；确认 `APP_ENV` |
| 数据写入少了一部分字段 | `upsert_rows` 丢弃模型中不存在的列 | `grep db.upsert_dropped_columns logs/platform.log`；`grep db.upsert_conflict_key_missing logs/platform.log` |
| 原始响应未留档 | `insert_raw` 异常被吞 | `grep db.raw_insert_failed logs/platform.log` |
| 调度任务没跑 | `SCHEDULER_ENABLED=false` 或 `APP_ENV=test` | `curl .../api/v1/system/jobs`（看 `running`）；`python scripts/platformctl.py status` |
| 单个任务反复失败 | 任务异常被 `_safe_run` 捕获，`last_status=failed` | `grep scheduler.task_error logs/platform.log \| tail` |
| AI 助手回答生硬/带「规则解释引擎」说明 | 未配置 `OPENAI_API_KEY`，或 LLM 调用失败降级 | `grep assistant.llm_failed logs/platform.log`；`grep assistant.context_error logs/platform.log` |
| 依赖/环境问题 | 虚拟环境缺失或依赖冲突 | `python scripts/platformctl.py doctor`（内部执行 `pip check`） |
| 未捕获异常 500 | 兜底处理器记 `app.unhandled_error` | `grep app.unhandled_error logs/platform.log \| tail` |
| **某个源「时通时断」，同一域名随机超时** | **本地 DNS 被污染**：同一域名反复解析出互不相关的假 IP（特征是出现 `2001::` 开头的 Teredo 地址） | `curl ".../api/v1/system/dns/diagnose?host=api.binance.com"`；看 `verdict` 是否为 `poisoned`，是则把「DNS 解析方式」改成 `doh`（详见《36 网络策略》§4） |
| **配了代理仍然全部失败，报 `Connection not allowed by ruleset`** | SOCKS5 握手与认证都通过后，CONNECT 被服务端返回 **REP=2（规则不允许）**，属代理侧白名单/套餐限制，与地址密码无关 | `python scripts/proxy_matrix_probe.py "user@ip:port"`；全部为 REP=2 即换代理或让供应商放行域名 |
| 后台显示「直连」但请求走了别的路径 | 进程环境变量 `HTTP_PROXY` 被 httpx 的 `trust_env` 静默采信 | 保持 `HTTP_TRUST_ENV=False`（默认）；`/api/v1/system/proxy` 会标明来源是否为 `env` |
| 配了代理但没生效 | 连接池未重建（旧连接仍在用） | 改配置后下一次请求会自动重建；若仍异常，`grep app.provider_proxy_restored logs/platform.log` 检查启动时的还原记录 |
| 报 `SOCKS 代理依赖缺失` | 缺 `httpx-socks` / `python-socks` / `socksio` | 按报错提示安装；离线环境用 `pip install --no-index --find-links data socksio` |
| 代理地址写错导致整类数据失败 | 归一化失败会抛 `proxy_error` 而非悄悄直连 | `grep proxy logs/platform.log`；按「标准写法 socks5://用户名:密码@IP:端口」重填 |
| 之前因连不上被自动停用的源，现在网络好了却还是停用 | 需显式批量恢复 | 页面「恢复被停用的源」或 `POST /api/v1/system/providers/reenable-stale`（默认不动人工手动禁用的源） |

## 已知局限 / 注意事项

- 健康状态、熔断计数、failover 事件全部存放在进程内存中（`ProviderHealthCenter` 的 `deque`，上限 20000/500），**进程重启即清零**，历史故障无法回溯，只能靠日志文件。
- `platformctl status` 解析 `/system/health` 时读取 `data.summary`，而该接口返回扁平结构，因此「数据源 共 N 个」这一行实际不会打印（详见「30 · 运维命令参考」）。
- 日志脱敏只按键名匹配，Provider 自己把密钥拼进 URL 或错误信息时仍可能出现在 `msg`/`exc` 中。
- 没有告警推送实现：故障只能靠主动查看 `/system/providers/dashboard` 或日志；`alert_admin` 策略只是分类标记。
- `logs/platform.log` 只保留 10 个 20 MB 分片，长期运行需自行归档；备份时只带最近 3 个日志文件。
- 页面上的「立即执行/一键测试/回填」等按钮在生产环境会因缺少 `X-Admin-Token` 失败，需要 curl 或代理层注入。
