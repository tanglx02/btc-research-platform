## 测试隔离机制（`conftest.py`）

- 导入 `app.*` 之前就固定 `APP_ENV=test`、`SCHEDULER_ENABLED=false`、`LOG_LEVEL=WARNING`；
- `DATABASE_URL` 指向 `data/_test_tmp/`（可用环境变量 `BTC_TEST_TMP` 改目录），**绝不触碰 `data/btc.db`**；
- `isolated_db` 是 autouse 夹具：每个用例一个 `test_{uuid4}.db`，并同时重置三个单例（`get_settings.cache_clear()`、`db.base` 的 engine/session_factory），用例结束后清理；
- `make_price_provider_factory` 提供可控失败的 `FakePriceProvider`（可指定失败次数与 `failure_type`），用于构造 failover 链路；
- `helpers.py` 的 `synthetic_series()` 用确定性正弦叠加而非随机数，保证可复现。

> **环境问题（非代码缺陷）**：在带「批量删除保护」的托管终端里跑全量测试，可能因夹具反复删除临时库而触发保护机制，表现为大量 `ERROR ... SystemExit: 1` 与
> `AssertionError: previous item was not torn down properly`。这不是项目代码的问题——单独跑任何测试文件都全绿。
> 规避方式是把临时目录指到不受保护的挂载点，或停用该保护后再跑：
> `BTC_TEST_TMP=/tmp/btc-test python -m pytest`。

## 真实环境演练（超出单元测试的部分）

单元测试用的是 Fake Provider，不触网。**「主 Provider 失效时系统还能不能干活」这种问题必须用真实数据源演练才有说服力**，
因此项目提供三个演练脚本，输出 JSON 报告到 `data/reports/`：

| 脚本 | 作用 | 用法 |
| --- | --- | --- |
| `scripts/provider_drill.py` | 27 个 Provider 逐个真实探测 + 14 个类别主备取数 + 主源失效演练 | `python scripts/provider_drill.py` |
| `scripts/alert_failover_drill.py` | 需求四十二专项：主源失效 / 全源失效下 Alert 的真实行为 | `python scripts/alert_failover_drill.py` |
| `scripts/backup_drill.py` | 备份—校验—恢复沙箱演练 + 篡改拒绝负向测试 | `python scripts/backup_drill.py` |

三个脚本都是**只读/沙箱**的：`provider_drill.py` 与 `alert_failover_drill.py` 在 `finally` 中复原所有被临时禁用的 Provider；
`backup_drill.py` 把备份写进临时目录，绝不覆盖线上库与 `.env`。

### 演练 2：需求四十二专项 —— 主 Provider 失效时 Alert 是否仍能工作

这是整套预警系统最关键的验收项。三个场景实测：

| 场景 | 操作 | 实测结果 |
| --- | --- | --- |
| A 基线 | 不动 | `satisfied=True` `would_notify=True` `quality=SINGLE_SOURCE` |
| B 主源失效 | 禁用 `market_price` 链首 | `satisfied=True` `would_notify=True` —— **经备用源继续可用** |
| C 全源失效 | 禁用整条链 | `quality=STALE` `used_fallback=True` **`would_notify=False`**，拦截理由「当前取到的是降级数据…本条规则要求数据新鲜，因此不触发提醒」 |

结论：**主源失效 → 自动切换，判定继续可用；全源失效 → 不伪造提醒、不崩溃，以明确的「不可用」收场。**

这里有一个容易误读的地方，值得单独说明：场景 C 的 `satisfied=True` 并不代表「发了邮件」。
`test_rule` 返回的是两层结果：

- `satisfied` —— 纯条件判定（拿当前能取到的值比阈值），回答「数值是否越过阈值」；
- `would_notify` —— 条件成立**且**通过质量门，回答「会不会真的发邮件」。

全源失效时数据降级为 STALE，`satisfied` 仍可能为真，但质量门（`require_fresh` 默认开启）必须把它拦下来。
**真正要守的是 `would_notify`**；断言写在 `satisfied` 上会得到似是而非的结论。

> 配套修正：默认 `min_quality` 由 `VERIFIED` 改为 `SINGLE_SOURCE`（`rules.py` 与前端 `pages-alerts.js` 同步）。
> 原因是 VERIFIED 要求同一时刻有 2 个以上数据源同时应答，真实网络里并不总能满足；
> 若默认 VERIFIED，用户按默认新建的第一条规则会「条件成立却永远收不到邮件」，直接违背「直至邮件到达」的主流程。
> 新鲜度拦截（`require_fresh` 默认 `True`）保持不变——那才是「不能用过期数据触发关键提醒」这条硬约束所在。

### 演练 3：备份 / 恢复（`backup_drill.py`）

沙箱内全流程实测：

| 步骤 | 结果 |
| --- | --- |
| 生成备份包 | ✅ 含 `btc.db` + `-wal` + `-shm`（WAL 一起打包，避免恢复后数据倒退）、配置、最近 3 个日志 |
| 签名校验 | ✅（SECRET_KEY 为默认值时降级为仅 SHA-256，并明确标注 `signature_strength=none`，不假装有效） |
| manifest 完整性 | ✅ 登记 5 个文件，3 个带 SHA-256 |
| 恢复库可只读打开 | ✅ 备份前 44 张表 → 恢复后 44 张表，一致 |
| 新增 alert 表随库备份 | ✅ 8 张 `alert_*` 表全部在恢复库中 |
| 篡改后拒绝恢复 | ✅ 校验返回 `ok=False`：「备份包内容与其记录的 SHA-256 不一致」 |
| 清单哈希不符被识别 | ✅ 发现 `db/btc.db`、`db/btc.db-shm` 两项不符 |

**演练中发现的真实注意点**：负向测试必须把 `.sig.json` 伴随文件一起复制。
只拷 `.tar.gz` 会命中「没有签名文件 → 跳过签名校验」的兼容分支，那时放行的不是验签机制通过，而是**根本没验签**。
脚本已修正为连同 sidecar 一起复制，并在报告中显式记录 sidecar 缺失时的行为：

```
[safe] sidecar 缺失时：ok=True —— 跳过签名校验，仅按清单校验文件哈希
```

这意味着：备份包被搬运时若丢失 `.sig.json`，验签层退化为仅靠**包内** manifest 的哈希兜底，
而 manifest 本身也在包内、理论上同样可被改。**结论：`.sig.json` 必须与 `.tar.gz` 一起保管，并在 `.env` 中设置强随机 `SECRET_KEY` 以启用真正的 HMAC 签名。**

## 已知局限 / 注意事项

- 单元测试不访问真实网络：Provider 全部是 Fake 实现；真实连通性要靠上面三个演练脚本单独验证。
- 没有前端自动化测试：`frontend/static/js/` 下没有 JS 测试文件，页面行为需人工验证。
- `--strict-markers` 意味着新增自定义标记必须先写进 `pytest.ini`，否则直接报错。
- `slow` 用例只在完整运行中执行；CI 若想快速回归应固定使用 `-m "not slow"`。
- 临时库目录 `data/_test_tmp/` 由用例自行创建、结束时清理单个文件，但目录本身不会被删除；`BTC_TEST_TMP` 可指向其他位置。
