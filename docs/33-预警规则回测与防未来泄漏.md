# 33 预警规则回测与防未来数据泄漏

一句话定位：让用户在保存规则前就看到「这条规则在过去会触发几次、触发后市场曾经怎么走」，并且**严格保证判定过程不碰未来数据**。

## 代码位置

| 位置 | 说明 |
| --- | --- |
| `backend/app/alerts/pipeline.py` | `backtest_rule()`、`_indicator_snapshot_at()`、`_build_ts_index()` |
| `backend/app/engines/indicators.py` | 指标序列导出（`series`） |
| `backend/app/api/alerts.py` | `POST /alerts/rules/{rule_id}/backtest` |

## 接口

```
POST /api/v1/alerts/rules/{rule_id}/backtest?max_bars=3000
```

`max_bars` 取值 200 ~ 20000，默认 3000（约 8 年日线）。

## 返回内容

| 字段 | 含义 |
| --- | --- |
| `available` | 是否成功回测（历史不足 / 规则不存在时为 false 并给出原因） |
| `trigger_count` | 历史触发次数 |
| `bars_tested` | 实际参与判定的 K 线根数 |
| `from_ts` / `to_ts` | 回测区间 |
| `first_trigger` / `last_trigger` | 首次 / 最近一次触发时间 |
| `avg_interval_days` | 平均触发间隔（天） |
| `trigger_dates` | 最近 50 次触发时间 |
| `aftermath` | 触发后 7 / 30 / 90 / 180 天的表现 |
| `caveats` | 必须向用户声明的局限 |

### 触发后表现（aftermath）

每一档窗口包含：

| 字段 | 含义 |
| --- | --- |
| `days` | 观察窗口 |
| `available` | 该档是否有足够未来数据 |
| `sample_size` | 有效样本数 |
| `avg_return_pct` | 平均涨跌幅 |
| `avg_max_gain_pct` | 期间最大涨幅 |
| `avg_max_drawdown_pct` | 期间最大跌幅 |
| `avg_volatility_pct` | 期间波动率 |
| `positive_ratio_pct` | 上涨样本占比 |
| `note` | 样本不足时的说明 |

**未来数据不足的窗口直接标 `available=False`，绝不用假数据凑数。**

## 防未来数据泄漏的实现

这是本模块最核心的工程约束，做法如下。

### 1. 因果切片（语义层）

回测从第 `WARMUP = 60` 根开始判定：

- 前 60 根只用于把指标"堆热"，**不产生判定**——否则等于用未来的数据预热再回测过去。
- 第 `i` 步时，`MetricContext` 收到的历史是 `candles[:i+1]`，即"截至该时点为止"。
- 历史分位、ATH/ATL、距 ATH 距离这些"截至当前"的统计量，都由 `MetricContext` 从 `candles[:i+1]` 现算。

### 2. 指标快照（性能层，等价但不改变结果）

早期实现是"每个时点都调用一次 `IndicatorEngine.compute(candles[:i+1])`"，在 3000 根日线上要跑 **75 秒**，接口直接超时。

现在改为**一次性算完指标序列，再按时间戳取快照**。之所以等价，是因为本项目全部指标序列都是**因果的**——第 `i` 个下标的值只由下标 ≤ `i` 的数据决定：

```
compute(candles[:i+1])[-1]  ≡  compute(candles)[i]
```

SMA / EMA / RSI / MACD / ATR / Bollinger / 已实现波动率 / 历史回撤 / 累计 VWAP 都满足这条性质。

**关键细节**：`IndicatorEngine` 导出 `series` 时会跳过 NaN 值（指标未成熟的早期点），因此序列长度与 K 线根数**不相等**，不能按下标索引。实现改用**时间戳二分查找**（`_build_ts_index` + `bisect_right`），对每个指标取"时间戳 ≤ 当前时刻的最后一个有效值"，这才是正确的因果对齐。

实测结果：耗时从 **74.88 秒降到 0.79 秒（约 95 倍）**，触发点集合完全一致。

### 3. 一致性守卫

以下两条测试锁死上述优化不会被破坏：

| 测试 | 作用 |
| --- | --- |
| `test_backtest_snapshot_matches_per_step_recompute` | 逐点比对快照取值与逐点重算，16 个指标全部吻合（1e-3 内） |
| `test_backtest_is_fast_enough_for_ui` | 1500 根回测必须在 15 秒内完成，拦住性能倒退 |

### 4. 反事实检验

`test_backtest_counterfactual_no_future_leak` 是本模块的**核心证明**：

1. 用完整历史回测，记录触发点集合。
2. **截掉最后 60 根**（这些是"未来"），重新回测。
3. 断言：
   - 截断后触发次数只会变少或持平（去掉未来数据不可能"多出"历史触发）；
   - **首个触发时点必须一模一样**——只要判定过程碰过未来数据，这个时点就会漂移；
   - 截断后最后一次触发不得晚于全量区间。

这与项目已有的 `18-防未来数据泄漏规范.md` 一脉相承。

### 5. 触发后表现只统计已存在的未来

```python
for i in hits:
    if i + days >= len(candles):
        continue   # 未来数据不够，这个样本直接不用（不补、不猜）
```

## 结果解读（面向非专业用户）

页面与邮件都必须明确说明：

- 这些数字只说明「过去这次条件成立之后，市场曾经出现过什么情况」，**不代表未来会重复**。
- 样本数越少，参考价值越低，请重点看 `sample_size`。
- 系统**不提供买卖建议**，也不对任何未来涨跌做承诺。

## 拒绝回测的情况

| 情况 | 返回 |
| --- | --- |
| 规则不存在 | `available=False` + "规则 N 不存在" |
| 规则无条件 | `available=False` + "该规则没有任何条件" |
| 历史 < 60 根 | `available=False` + "本地只有 N 根日线…请先执行历史回填" |
| 指标算不出来 | `available=False` + "指标计算失败" |

绝不返回一个"看起来正常"的空结果误导用户。
