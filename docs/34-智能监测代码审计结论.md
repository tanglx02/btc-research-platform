# 34 代码审计结论（智能监测模块开发前）

一句话定位：开发「智能监测、条件预警与邮件通知」之前，对现有项目做的 11 项审计，以及据此确定的复用/新增/冲突边界。

审计时点：本模块开发开始之前。以下每一条都对应真实文件，不是假设。

## 1. 当前数据获取方式

| 事实 | 位置 |
| --- | --- |
| 业务层**从不**直接发 HTTP 请求，一律经过 `MarketService` 等 service | `backend/app/services/` |
| 每个 service 方法内部走 `ResilientRouter`，自动选主源、失败切备源 | `backend/app/providers/router.py` |
| 采集结果同时写 Raw 与 Normalized 两张表，幂等写入 | `backend/app/db/repo.py` |
| 本地历史优先：读历史时先查库，够用就不再请求外部 | `backend/app/services/market_service.py` |

**结论：Alert 取值一律通过 service，不碰 transport 层。**

## 2. 当前 Provider 结构

| 事实 | 位置 |
| --- | --- |
| 注册了 **27 个** Provider 实例（实测 `registry._providers` 长度 27） | `backend/app/providers/impl/`（10 个实现文件，另有 `mock_faulty.py` 仅测试用） |
| 抽象基类 `DataProvider`：声明 categories / capabilities / priority | `backend/app/providers/base.py` |
| 注册表自动发现（`registry.autodiscover`），支持按能力查询 | `backend/app/providers/registry.py` |
| 健康评分、熔断 cooldown、恢复阈值 | `backend/app/providers/health.py` |
| 交叉验证五态（`VERIFIED` / `CROSS_VERIFIED` / `SINGLE_SOURCE` / `STALE` / `MISSING`） | `backend/app/providers/validation.py` |
| 统一传输层（超时、重试、限流） | `backend/app/providers/transport.py` |

**结论：Alert 不自己选 Provider，只消费 router 给出的结果与来源标记。**

## 3. 当前任务调度结构

| 事实 | 位置 |
| --- | --- |
| 单一 `SchedulerManager`，任务以 `_build_jobs()` 列表声明 | `backend/app/scheduler/manager.py:50` |
| 原已有 12 个任务：market_tick / market_1h / market_1d / derivatives / onchain / sentiment / macro / etf / quality / gap_repair / health_probe / raw_retention | 同上 52-90 行 |
| 每个任务带 `priority`，按优先级与周期调度 | 同上 |

**结论：预警直接**追加**3 个任务，不新建调度器。**

## 4. 当前指标结构

| 事实 | 位置 |
| --- | --- |
| `IndicatorEngine`，版本号 `ind_v1` | `backend/app/engines/indicators.py:150` |
| 指标函数全部为滚动窗口函数（因果） | 同上 22-140 行 |
| 一次计算返回 `latest` + `series` + `meta` | 同上 169 行 |

**结论：Alert 复用同一个引擎实例，不重算一套指标。**

## 5. 当前数据库结构

| 事实 | 位置 |
| --- | --- |
| SQLAlchemy 2.0 async + SQLite(aiosqlite)，可切 PostgreSQL/TimescaleDB | `backend/app/db/base.py` |
| 原有 **36** 张表，集中在单一 models 文件 | `backend/app/db/models.py` |
| 主键统一用 `PK_BIGINT`（SQLite 兼容写法） | 同上 |
| 表注册进 `ALL_TABLES`，由 `init_db()` 建表 | `backend/app/db/model_registry.py`、`migrate.py` |

**结论：新增 8 张 `alert_*` 表，命名与主键风格与现有完全一致。原有 36 张表不动。加入本模块后 `ALL_TABLES` 共 44 张。**

## 6. 当前用户系统

| 事实 | 位置 |
| --- | --- |
| 单用户本地部署形态，写操作靠 `X-Admin-Token` 保护 | `backend/app/api/deps.py` 的 `WriteDep` |
| 无多租户、无注册登录 | 同上 |

**结论：规则与渠道沿用同一套 `WriteDep` 写保护，不引入用户体系。**

## 7. 当前配置系统

| 事实 | 位置 |
| --- | --- |
| Pydantic Settings，从 `.env` 读取，带默认值 | `backend/app/core/config.py` |
| 已有 `JOB_*` 系列任务周期配置、Provider key 配置 | 同上 |

**结论：预警配置以 `ALERTS_ENABLED` / `JOB_ALERT_*` / `ALERT_DIGEST_*` / `SMTP_*` 追加，命名沿用现有风格。**

## 8. 当前日志系统

| 事实 | 位置 |
| --- | --- |
| 结构化单行 JSON 日志，带 `request_id` / `provider` / `env` | `backend/app/core/logging.py` |
| 事件式调用 `logger.event("xxx", key=value)` | 全项目一致 |

**结论：预警日志沿用同一 logger，事件名统一 `alert.*` 前缀。**

## 11. 可能产生冲突的地方（已识别并规避）

| 风险 | 规避方式 |
| --- | --- |
| 指标目录与既有 `IndicatorEngine` 字段重名不一致 | 取值器统一从 `ctx.indicators` 读，字段名与引擎输出逐一对齐 |
| 与现有 Scheduler 争抢 Provider 配额 | 预警任务优先级设为 20/21/22（低于采集任务），且**一个周期只取数一次** |
| 与既有 `docs/18-防未来数据泄漏规范` 冲突 | 回测严格复用同一因果原则，并用反事实检验证明 |
| 写接口越权 | 沿用 `WriteDep` |
| `dataclass(slots=True)` 不可挂临时属性 | 交叉条件改为显式传参 `_eval_transition(..., ctx=ctx)` |
| 价格类阈值被资金流负数误判 | 正值约束只对 `_PRICE_LIKE` 集合生效 |

## 审计结论

**现有架构足以承载本功能，不需要任何推倒重建。**

- Provider / Failover：直接复用，Alert 只消费结果。
- Scheduler：只在 `_build_jobs()` 追加 3 个任务。
- 指标：复用同一引擎。
- 数据库：新增 8 张表，原有 36 张不动（合计 44 张）。
- 前端：新增 1 个 JS 文件 + NAV 分组，原有页面渲染体系不变。
- API：新增 `/api/v1/alerts` 子路由，原有接口行为零改动。
