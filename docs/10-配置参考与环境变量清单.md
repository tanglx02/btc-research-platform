### 0.2 后台配置中心（推荐方式）

对应「所有配置都能在后台配置」这一目标，新增 `app_settings` 表 + `core/settings_store.py`。

**优先级**：后台配置（数据库） > `.env`/环境变量 > 代码默认值。

| 组成 | 位置 | 职责 |
|---|---|---|
| `app_settings` 表 | `db/models.py` | 只存 `key -> value`，不存元数据 |
| `SETTINGS_SPEC` | `core/settings_store.py` | 56 项配置的元数据：中文名、说明、类型、是否敏感、是否需重启、枚举选项 |
| `SettingsStore` | `core/settings_store.py` | 进程内缓存 + 落库；`apply_to_settings()` 把值写回 settings 单例 |
| API | `api/system.py` | `GET/PUT /system/settings`、`POST /system/settings/reset`、`GET /system/settings/keys` |
| 前端 | `pages-system.js` 的 `P.settings` | 表单由元数据驱动渲染，后端新增配置项前端无需改代码 |

**为什么「改完不用重启」**：保存后 `apply_to_settings()` 会 `setattr` 回 settings 单例，
于是所有原本读 `settings.XXX` 的模块自动拿到新值——告警、数据源、采集器都不需要感知配置中心的存在。

**敏感值只写不读明文**：`SMTP_PASSWORD`、`*_API_KEY`、`SECRET_KEY`、`ADMIN_TOKEN` 等 8 项
标记为 `sensitive`，列表接口只回传 `has_value` 与掩码（如 `tes************456`），原文永不下发前端。

**恢复默认**：`POST /system/settings/reset` 删除库里的覆盖值。实现上靠 `_baseline` 快照还原
——因为 `setattr` 已经把原值冲掉，只删库记录是变不回去的（这一点曾真实踩坑，已由
`test_reset_restores_baseline_value` 锁定）。

**不暴露的配置**：`DATABASE_URL`、`HOST` 不在可配列表内——改错会直接导致服务起不来，属于部署期配置，应走 `.env`。

**必须重启才生效的 3 项**：`PORT`（监听端口）、`SCHEDULER_ENABLED`（是否启动调度器）、`SECRET_KEY`（已被 `scripts/backup.py` 读取用于签名）。
其余 48 项保存即生效；页面上会明确标注「需重启」。

**数据源密钥**：`GLASSNODE_API_KEY` / `CRYPTOQUANT_API_KEY` / `COINGLASS_API_KEY` / `FRED_API_KEY`
在「系统设置 → 数据源密钥」填写即可。`ProviderBase.api_key()` 的读取顺序已改为
**配置中心 → `.env`**，填完立即生效，不需要重启，也不需要重新注册 Provider。

### 4.1 关于 `HTTP_TRUST_ENV` 为什么默认关闭（排障陷阱）

httpx 客户端默认 `trust_env=True`，会**静默读取进程环境变量** `HTTP_PROXY` / `HTTPS_PROXY` / `ALL_PROXY`。
一旦操作系统或 Docker 镜像里残留了这些变量，就会出现：

> 后台显示「未配置代理、直连」，但请求实际被环境变量里的代理接管，且毫无日志痕迹。

这与本项目「浏览器可见即可追源」的要求冲突，因此默认关闭：平台只认自己后台配置的那三项。
确实需要依赖环境变量部署的场景（例如出口统一走公司代理），把它打开即可，
此时「系统设置 → 网络与代理」会显示该代理来源为「环境变量」。

## 9. `ADMIN_TOKEN` 与 `SECRET_KEY` 的真实用途

两者常被混淆，此处按代码明确区分。

### 9.1 `ADMIN_TOKEN` → 写接口鉴权（`X-Admin-Token`）

`backend/app/api/deps.py`：

| 依赖 | 行号 | 校验逻辑 | 使用者 |
|---|---|---|---|
| `require_admin` | 26-37 | 非生产直接返回 `"dev"`；生产下缺头 → `ForbiddenError`；不匹配 → `UnauthorizedError` | `AdminDep`（57）：`/system/providers/test-all`、`PATCH /system/providers/{name}`、`POST /system/jobs/{id}/run`、`POST /system/backfill` |
| `require_write_permission` | 40-53 | 同上逻辑，返回 `"user"` | `WriteDep`（58）：资金计划/交易写入、回测等 |

两个函数都用 `secrets.compare_digest` 做**常量时间比对**，
注释（`deps.py:43-44`）记录了一个已修的严重缺陷：
「早期版本只判断『请求头是否存在』，任意非空字符串都能通过，等于写接口完全不设防。」

**重要**：非生产环境（`APP_ENV != production`）两个依赖都直接返回，不做任何校验 ——
这是刻意的本地开发便利，因此**部署到公网前必须把 `APP_ENV` 设为 `production`**。

请求头名 `X-Admin-Token` 已在 CORS `allow_headers` 中放行（`main.py:123`）。

### 9.2 `SECRET_KEY` → 备份包 HMAC-SHA256 签名

`scripts/backup.py`：

| 环节 | 函数 | 行号 | 说明 |
|---|---|---|---|
| 生成签名 | `write_signature` | 80-100 | 计算归档文件 SHA-256，再用 `SECRET_KEY` 对 `文件名:摘要` 做 HMAC-SHA256，写 `.tar.gz.sig.json` |
| 占位检测 | `_is_placeholder_secret` | 72-73 | 空串或以 `change-me` 开头即视为占位密钥 |
| 占位时的处理 | — | 89-91 | `signature_strength` 标为 `none（...请在 .env 中设置强随机值后再备份）`，**不写 `hmac_sha256`**，即明确不假装有效防护 |
| 恢复前校验 | `verify_signature` | 103-131 | 见下表 |
| 恢复入口 | `restore_backup` | 284-288 | 校验不通过**直接中止**，不做「看起来能解压就放行」 |

`verify_signature` 的判定矩阵：

| 情形 | 返回 | 说明 |
|---|---|---|
| 无 `.sig.json`（老备份/手工搬运丢失） | `(True, …)` | 跳过签名校验，仅按清单哈希复核 |
| `.sig.json` 无法解析 | `(False, …)` | 中止 |
| SHA-256 与记录不一致 | `(False, …)` | 中止，「文件已损坏或被替换」 |
| 有记录但无 `hmac_sha256` | `(True, …)` | 只完成了 SHA-256，提示生成时密钥为占位值 |
| 有 HMAC 但当前 `SECRET_KEY` 是占位值 | `(False, …)` | 中止，要求先把密钥改成与备份时一致 |
| HMAC 不匹配 | `(False, …)` | 中止，「不是由持有当前 SECRET_KEY 的一方生成，或文件被篡改」 |

`backup.py:57-59` 的注释对防护边界有诚实说明：

> 注意：不等于防篡改 —— 密钥与备份放在同一台机器上时，攻击者可同时拿到两者。
> 它真正防止的是「备份文件在搬运过程中损坏或被无意替换」。

此外，`SECRET_KEY` 还在 `config.py:156-157` 参与生产启动校验；
除此之外**没有**用于会话签名、JWT 或任何加密用途。
