## 六、如何配置 SMTP

### 方式 A：页面配置（推荐，优先级更高）

进入「智能监测 → 邮件设置」，填写：Server / Port / 加密方式（SSL/TLS/无）/ 用户名 / 密码或授权码 / 发件人 / 收件人，保存后点「发送测试邮件」。

### 方式 B：环境变量

`.env` 中设置：

```
SMTP_HOST=smtp.qq.com
SMTP_PORT=465
SMTP_ENCRYPTION=ssl
SMTP_USER=you@qq.com
SMTP_PASSWORD=你的授权码
SMTP_SENDER=you@qq.com
SMTP_SENDER_NAME=BTC 智能监测
SMTP_TO=you@qq.com
PUBLIC_BASE_URL=http://你的地址:8000
```

**注意**：国内邮箱一般要填**授权码**，不是登录密码。页面配置始终优先于环境变量。

## 七、如何创建第一条监测规则

1. 打开「智能监测 → 规则 → 新增规则」。
2. 监测数据选 **【BTC 当前价格】**（每个指标旁有通俗解释）。
3. 条件选 **【低于】**，阈值填 **90000**。
4. 持续填 **10 分钟**（避免瞬时插针误报）。
5. 触发后选 **【发送邮件】**。
6. 冷却选 **24 小时**。
7. 可先点 **【测试规则】**，系统会用当前数据立即告诉你是 ✅ 满足还是 ❌ 不满足。
8. 保存。此后后台持续运行，条件成立时自动发信；条件恢复后再次跌破会重新通知。

## 十、确认主 Provider 失效后能够自动切换

**机制**：Alert 取值一律经 `MarketService` → `ResilientRouter`，由 router 负责主备切换、熔断与恢复；Alert 不自己选源，只消费结果与来源标记。

**实际观测**：验证期间 binance 超时被 `auto_disable`，stooq 报 `data_format_error`，yahoo_macro 返回 403，frankfurter 报 `unsupported_input`——在多个源相继失败的情况下，**Alert 求值仍然返回判定结果而非崩溃**。

**测试锁定**：`test_alert_works_when_primary_provider_fails`、`test_build_context_records_fallback_state`。

**真实演练**（`scripts/alert_failover_drill.py`，调用 `AlertPipeline.test_rule` 走真实 router）：

| 场景 | 操作 | 实测 |
| --- | --- | --- |
| A 基线 | 不动 | `satisfied=True` `would_notify=True` `quality=SINGLE_SOURCE` |
| B 主源失效 | 禁用 `market_price` 链首 `binance_vision` | `satisfied=True` `would_notify=True` —— 经备用源继续取到真实价 |
| C 全源失效 | 禁用整条链 | `quality=STALE` `used_fallback=True` **`would_notify=False`**，拦截理由「当前取到的是降级数据…本条规则要求数据新鲜，因此不触发提醒」 |

**主源失效演练**（`scripts/provider_drill.py`，禁用链首后重新取数）：

| 类别 | 结果 |
| --- | --- |
| `market_price` / `market_ticker_24h` / `ohlcv` | ✅ 自动切到 gate |
| `onchain_basic` | ✅ 自动切到 blockchain_info_stats |
| `macro_series` | ✅ 自动切到 frankfurter |
| `market_cap` / `sentiment_index` | ❌ 无备用源可切（链宽仅 1，见下） |

> **如实告知的局限**：`market_cap`（仅 coingecko）与 `sentiment_index`（仅 alternative_me_fng）的 Provider 链只有 1 个成员；
> `orderbook`、`derivatives_liquidation`、`onchain_advanced`、`exchange_flow`、`etf_flow` 的现有成员全部需要 API Key 而未配置。
> 这些类别在主源失效时**没有可切换的备用源**，系统抛 `AllProvidersFailedError` 明确报错（绝不编造数值），
> 依赖它们的预警规则会**静默不触发**——不会误报，但也不会送达。补配对应 API Key 才能把这些链补宽。

**来源留痕**：事件中记录 `provider`（实际使用的源）与 `data_quality`，邮件中显示「主要数据源 / 实际数据源链 / 故障切换 / 数据质量」。

## 十一、确认邮件失败会自动重试

**机制**：触发时**先落库**（`PENDING`），再尝试发送。发送失败只更新 `notification_status=FAILED`，事件本身不动；`alert_retry` 任务每 300 秒扫 PENDING/FAILED 事件补发。

**关键设计**：`inline attempts`（同一时刻连续尝试，上限 `MAX_SEND_ATTEMPTS=3`）与 `retry_count`（补发轮次，每轮 +1）**分离**。早期实现里一次瞬时故障就会耗尽补发预算，已修正。

**熔断**：连续失败 5 次（`CHANNEL_FAILURE_THRESHOLD`）后渠道冷却 1800 秒，避免无效发信风暴；冷却结束自动恢复。

**测试锁定**：`test_failed_notification_keeps_event_and_retries`、`test_email_send_network_error_is_retried`、`test_channel_circuit_breaker_after_repeated_failures`。

## 十二、确认 Alert 事件不会丢失

| 保障 | 说明 |
| --- | --- |
| 先落库再发送 | 事件写入与通知解耦，发信失败不影响事件存在 |
| 无渠道也不丢 | 没有可用渠道时标 `SKIPPED`，事件保留 |
| 有限重试 | 最多 `retry_count` 轮，不无限重试 |
| 失败可见 | 每次尝试写 `alert_notification_logs`，含 SMTP 响应原文与错误 |
| 连续失败告警 | 达到阈值在日志与系统通知中明确提示「邮件通知服务异常」 |
| 页面可查 | 用户随时能看到哪些提醒还没发出去、为什么 |

**测试锁定**：`test_no_channel_marks_skipped_not_lost`、`test_send_success_marks_event_sent`。
