## 1. 问题背景

平台要拉取 Binance、Coinbase、Kraken、Gemini、Bitfinex、CoinGecko 等海外数据源。
在国内网络环境下会同时遇到两类问题，它们**症状相似但根因完全不同**，因此处置方式也不同：

| 症状 | 真因 | 处置 |
|---|---|---|
| 一直连不上，稳定超时 | 目标被网络层阻断 | **配代理**（本文第 2、3 节） |
| 时好时坏，同一数据源随机超时 | **本地 DNS 被污染**，解析到假 IP | **改用 DoH 解析**（本文第 4 节） |
| 后台显示「直连」但实际走了别的代理 | 进程环境变量 `HTTP_PROXY` 被 httpx 静默采信 | 保持 `HTTP_TRUST_ENV=False` |

排错的第一个动作永远是：**先分清是「连不上」还是「解析错」**。
用 §5 的 `proxy_matrix_probe.py` 与 `/system/dns/diagnose` 可以直接区分。

## 2. 代理配置

### 2.1 配置位置

后台「系统设置 → 网络与代理」，三项，**保存后下一次请求即生效，不需要重启**。

| 配置项 | 说明 | 优先级 |
|---|---|---|
| `SOCKS_PROXY` | SOCKS5 代理，推荐 | **最高** |
| `HTTPS_PROXY` | HTTP/HTTPS 正向代理 | 次 |
| `HTTP_PROXY` | 兜底 | 最低 |

除全局配置外，**单个数据源还能配独立代理**（优先级高于全局），见 §2.3。

### 2.2 地址写法容错

用户从供应商页面复制出来各式各样，因此做了归一化（`core/proxy.py`）：

| 你粘贴进来 | 归一化结果 |
|---|---|
| `proxy:2048507772t@43.213.7.34:1080` | `socks5://2048507772t@43.213.7.34:1080` |
| `socks5，proxy:user@1.2.3.4:1080`（中文标点） | `socks5://user@1.2.3.4:1080` |
| `socks5h://u:p@h.example:1080` | `socks5://u:p@h.example:1080` |
| `user@1.2.3.4:1080`（只带用户名） | `socks5://user@1.2.3.4:1080` |
| `1.2.3.4:1080`（无认证无 scheme） | `socks5://1.2.3.4:1080` |
| `socks5://u@host`（省略端口） | `socks5://u@host:1080` |
| `[::1]:1080` | `socks5://[::1]:1080` |

无法识别的地址会**明确报错 `proxy_error`**，而不是悄悄退回直连 ——
后者会让用户误以为「数据源坏了」，把排查方向彻底带偏。

> 底层库 `python-socks` 不认 `socks5h` 这种写法，所以必须归一化后再交给它。

### 2.3 单个数据源独立代理

```http
PATCH /api/v1/providers/binance
X-Admin-Token: <token>
{"proxy": "socks5://user:pass@1.2.3.4:1080"}
```

- 留空字符串 `""` = 回到「跟随全局代理」；
- 真实地址写入 `providers.proxy` 列，**进程重启后由 `HealthService.restore_proxy_overrides()` 自动还原**；
- 修改会立即关闭该 Provider 的旧连接池，下一次请求走新代理。

### 2.4 改完立即生效的实现要点

连接池是复用的，所以「改了配置」不等于「改了连接」。
`ProviderTransport` 缓存了**建连接时用的代理**（`_client_proxy`），每次取连接时比对，
不同就关闭旧池重建。这是「后台保存后立即生效」的关键。

### 2.5 单次代理写入库的敏感度

代理密码属于凭据，因此：

- 列表/诊断接口只返回掩码形式（`socks5://user:***@1.2.3.4:1080`）；
- `describe_proxy()` 返回结构里有 `has_password`，但**绝不返回密码明文**；
- 单元测试 `test_mask_never_leaks_password` 会断言 `json.dumps(info)` 里也不含明文。

## 3. 代理测试与诊断

### 3.1 页面一键测试

「系统设置 → 网络与代理」提供三个按钮：

| 按钮 | 行为 |
|---|---|
| 测试代理连通性 | 用填写的地址真实请求若干目标，逐项回报状态码与耗时 |
| 直连对照测试 | **强制绕过代理**做同样请求，用来对比「配之前」的基线 |
| 保存为全局代理 | 按 scheme 落到 `SOCKS_PROXY` 或 `HTTPS_PROXY` |

探测目标里刻意包含一个「回显自己出口 IP」的中立站点。
**只有它成功，才能证明请求真的走了代理**，否则可能只是碰巧直连成功。

> 直连对照测试必须强制绕过环境变量代理（实现上给 transport 传 `allow_global_proxy=False`），
> 否则在注入了 `HTTP_PROXY` 的终端里，所谓「对照组」其实也走了代理，两边结果一样，失去意义。

### 3.2 命令行矩阵探测

```bash
python scripts/proxy_matrix_probe.py "2048507772t@43.213.7.34:1080" --timeout 15
```

对「SOCKS5 / HTTP CONNECT」×「一系列目标」做矩阵探测，输出 SOCKS5 拒绝码含义：

| REP | 含义 | 判定 |
|---|---|---|
| 0 | 成功 | 目标可用 |
| 2 | **规则不允许** | 代理侧白名单/套餐限制，与地址密码无关 |
| 3 | 网络不可达 | 代理自身出口问题 |
| 4 | 主机不可达 | 目标侧问题 |
| 5 | 连接被拒 | 目标拒绝连接 |

**`REP=2` 是最常见的误判点**：握手与用户名密码认证都已通过，
才在 CONNECT 阶段被拒 —— 说明账号没问题，只是代理服务器不允许访问该目标。
这时应当换代理，或让供应商放行域名，而不是反复检查地址。

### 3.3 对照演练（确定哪些源因代理而恢复）

```bash
python scripts/proxy_drill.py
```

输出 `data/reports/proxy_drill_*.json`，含 `gained_via_proxy`（配代理后新增可用）与
`still_unreachable`（仍然不可用）。

### 3.4 恢复被停用的数据源

曾有源因为连不上被策略自动停用，现可用后：

- 后台「数据源中心」页头的「恢复被停用的源」按钮；
- 或 `POST /api/v1/system/providers/reenable-stale`。

注意 `reenable_disabled(include_manual=False)` **默认只恢复被系统自动停用的源，
不翻过人工手动禁用** —— 避免覆盖人的决定。

## 4. DNS 污染与 DoH

### 4.1 症状识别

同一域名反复解析到互不相关的 IP，例如实测 `api.binance.com`：

```
getaddrinfo -> 31.13.80.169          （另一家公司的地址段）
getaddrinfo -> 2001::9f6a:794b       （Teredo 保留段，一看就是假的）
getaddrinfo -> 108.160.172.204       （这一次才是真的）
```

污染包与真实应答抢答，谁先到用谁 —— 于是表现为**随机的间歇性超时**，
极具迷惑性，常被误判为「墙」或「数据源不稳定」。

### 4.2 处置

把「DNS 解析方式」改成 `doh`：查询包封装进 HTTPS 发给 DoH 服务器，污染者抢答不了。
实现要点：

1. 取到真实 IP 后，把请求 URL 的 host 换成 IP；
2. **同时必须保留原域名的 `Host` 头与 TLS SNI**（`extensions["sni_hostname"]`），
   否则 https 会因证书校验失败而断连，且报错会把人引向错误方向；
3. 结果的 TTL 缓存，避免每个请求多耗一次往返。

### 4.3 DoH 服务器怎么选（国内部署的关键）

**默认端点一定不能照搬国外文档**。实测（同一台国内部署机，6 秒超时）：

| 端点 | 结果 | 结论 |
|---|---|---|
| `https://dns.alidns.com/dns-query` | 可达，约 0.4s | **国内首选** |
| `https://doh.pub/dns-query`（DNSPod/腾讯） | 可达 | 备用 |
| `https://cloudflare-dns.com/dns-query` | **连不上（000）** | 仅作最后兜底 |
| `https://dns.google/dns-query` | 连不上 | 仅作最后兜底 |

因此默认值排成 `alidns → doh.pub → cloudflare → google`。
如果把 Cloudflare 排在第一位，用户会遇到「改成了 DoH 却毫无效果」，
进而误以为这个功能坏了 —— 这是纯粹的默认值选择问题，不是代码问题。

### 4.4 两种协议都要问一遍

各家 DoH 服务支持的格式并不统一，`core/dns_resolver.py` 因此两条路都走：

| 形式 | 请求 | 支持的服务器 |
|---|---|---|
| JSON（RFC 8427） | `?name=<域名>&type=A` | Cloudflare、Google、DNSPod |
| **二进制报文（RFC 8484）** | `?dns=<base64url(DNS 报文)>` | **阿里公共 DNS 只认这一种** |

先用 JSON 问，**该降级时**再自动改用报文形式问同一个端点。
好处很直接：用户从任何渠道抄来的 DoH 地址都能直接用，不需要先去搞清楚它是哪种方言。
`_decode_dns_answer()` 自己做报文解析，支持 DNS 压缩指针。

#### 什么时候**不该**降级

不是所有失败都值得换成报文再问一次。`_worth_retrying_as_wire()` 的判定：

| 失败原因 | 换报文重试 | 理由 |
|---|---|---|
| `400` / `415` 等 4xx | ✅ 重试 | 服务器明确表示「不接受 JSON 形式」，换一种格式正是解法 |
| 回了非 JSON 内容 | ✅ 重试 | 同上，属于协议不匹配而非故障 |
| `ConnectError` / `ReadTimeout`（`TransportError`） | ❌ 直接放弃 | 端点不可达，报文形式发到同一个坏服务器上照样超时 |
| 5xx | ❌ 直接放弃 | 端点自身故障，换格式救不了 |

如果无条件重试，4 个端点 × 2 种查询类型（A/AAAA）下，一次整体故障最坏要多付 8 次徒劳往返 ——
而这段时间业务请求正卡在这儿。降级失败后该端点会进 60 秒熔断，期间不再尝试。

### 4.5 边界（刻意不做的事）

| 情况 | 行为 | 理由 |
|---|---|---|
| **已配置代理** | 不启用 DoH | 走代理时解析发生在代理侧，本地改写毫无意义 |
| **DoH 服务器连不上** | 静默退回系统 DNS | 新功能只能「把坏的变好」，不能把本来能用的搞坏 |
| **IP 字面量目标** | 不解析 | 没有 DNS 污染问题，纯浪费一次往返 |

### 4.6 污染检测接口

```http
GET /api/v1/system/dns/diagnose?host=api.binance.com
```

同时返回：本地 DNS 答案、DoH 真实答案、判定（`clean` / `suspicious` / `poisoned`）与行动建议。

## 5. 依赖与部署

SOCKS5 支持依赖三个包，若缺失会**明确报 `proxy_error` 并给出安装命令**，不会悄悄直连：

```bash
pip install httpx-socks python-socks socksio
```

离线环境：

```bash
pip download socksio -d data/ --no-deps
pip install --no-index --find-links data socksio
```
