# 03 数据源注册表与数据源清单

一句话定位：系统接了哪些数据源、各自覆盖什么、谁需要 API Key、注册表如何工作。

## 代码位置

| 文件 | 职责 |
| --- | --- |
| `backend/app/providers/base.py` | `DataProvider` 抽象基类 |
| `backend/app/providers/registry.py` | 注册表与自动发现 |
| `backend/app/providers/impl/` | 27 个 Provider 实现（10 个实现文件） |
| `backend/app/providers/types.py` | `DataCategory`、`QualityStatus`、`ProviderResult` 等 |

## 注册机制

- 启动时 `registry.autodiscover()` 扫描 `impl/` 目录并实例化，输出 `app.providers_registered count=27`。
- 每个 Provider 声明 `categories`（能供什么数据）、`capabilities`（细粒度能力）、`default_priority`（优先级）。
- 注册表支持按 category 查询候选链；未配置 API Key 的 Provider 状态为 `NOT_CONFIGURED`，**系统不会用假数据顶替**。
- 可通过 `PROVIDER_OVERRIDES`（JSON）覆盖主源顺序、禁用某个源。

## API Key 怎么填（推荐在后台填，不用改 .env）

需要 Key 的 Provider（`api_key_env` 非空）在启动时按以下顺序取值：

1. **配置中心（数据库 `app_settings` 表）** —— 后台「系统设置 → 数据源密钥」里填的值；
2. **环境变量 / `.env`**；
3. 空 —— 则判定为未配置。

也就是说：**在后台填完点保存即刻生效，不需要重启服务，也不需要碰 `.env`**。实现见 `ProviderBase.api_key()`（`backend/app/providers/base.py`）与 `backend/app/core/settings_store.py`。

27 个数据源里只有 4 个需要 Key，其余全部免密钥可用：

| Provider | 环境变量 / 配置 key | 影响的能力 |
| --- | --- | --- |
| `coinglass_etf` | `COINGLASS_API_KEY` | ETF 资金流 |
| `cryptoquant_etf` | `CRYPTOQUANT_API_KEY` | ETF 资金流 |
| `glassnode` | `GLASSNODE_API_KEY` | 链上进阶指标 |
| `fred` | `FRED_API_KEY` | 宏观序列（利率 / M2 等） |

这 4 个 key 都已在后台「系统设置 → 数据源密钥」分类中列出，**不存在「必须手工改 .env 才能配」的数据源**。

后台已配置的 Key 只回传掩码（如 `abc************xyz`）与「已配置」标记，**接口与页面都不返回明文**；要换 Key 就填一个新的覆盖，要清除就点该项的「清除」（等于 `POST /system/settings/reset`）。

## 未配置 Key 时的行为

对应 Provider 状态为 `NOT_CONFIGURED`，不参与候选链。页面会在「数据源中心」明确显示该状态，**系统绝不生成替代数据**。

「数据源中心」页面顶部有指向「系统设置」的入口，看到 `NOT_CONFIGURED` 且该源需要 Key 时，直接去那里填即可。

## 每个数据源可以单独配走哪个网络出口

除全局代理外，单个数据源支持**独立代理**（优先级高于全局），适合「只有某几家需要代理」的情形：

```http
PATCH /api/v1/providers/binance
{"proxy": "socks5://user:pass@1.2.3.4:1080"}
```

留空字符串即回到「跟随全局」。真实地址写入 `providers.proxy` 列，进程重启后由
`HealthService.restore_proxy_overrides()` 自动还原，无需重新配置。

## 数据源「时通时断」先查 DNS，别急着断定是墙

实测本机 `api.binance.com` / `api.coinbase.com` 等被污染：同一域名反复解析出互不相关的 IP，
尤其常见 Teredo 保留段 `2001::xxxx`。表现为随机超时，极易被误判为数据源不稳定。

用 `GET /system/dns/diagnose?host=...` 一键对比本地 DNS 与 DoH 权威答案，
判定为污染时把「DNS 解析方式」改为 `doh` 即可。详见《36 · 网络策略：代理与 DNS 解析》。

## 实测说明

验证期间曾观测到：binance 超时被自动禁用、stooq 报 `data_format_error`、yahoo_macro 返回 403、frankfurter 报 `unsupported_input` —— 多个源相继失败时，上层仍然返回判定结果而非崩溃，这正是主备切换在起作用。

> 另有一类失败与上述都无关：代理的 SOCKS5 CONNECT 返回 **REP=2（规则不允许）**。
> 握手与认证都已通过却在放行环节被拒，属于代理服务端限制，应换代理或让供应商授权，
> 而不是反复检查地址与密码（详见《36》§3.2）。
