## 启动校验（`validate_for_startup()`）

`APP_ENV=production` 时：

- `SECRET_KEY` 仍以 `change-me` 开头 → `RuntimeError("生产环境必须设置 SECRET_KEY 环境变量")`；
- `ADMIN_TOKEN` 仍以 `admin-change-me` 开头 → `RuntimeError("生产环境必须设置 ADMIN_TOKEN 环境变量")`。

随后确保 `DATA_DIR` / `LOG_DIR` / `BACKUP_DIR` 目录存在。生成强随机串的建议（`.env.example` 注释）：`openssl rand -hex 32`。

## 鉴权方式

| 依赖 | 生效条件 | 规则 |
| --- | --- | --- |
| `AdminDep`（`require_admin`） | 仅 `APP_ENV=production` | 请求头 `X-Admin-Token` 必须存在且**等于** `ADMIN_TOKEN`，否则 401 `unauthorized`；非生产环境直接返回 `"dev"` |
| `WriteDep`（`require_write_permission`） | 仅 `APP_ENV=production` | 请求头 `X-Admin-Token` 只要**非空**即放行（不与 `ADMIN_TOKEN` 比对），缺失返回 403 `forbidden` |

需要 Admin 的接口：`POST /system/providers/test-all`、`PATCH /system/providers/{name}`、`POST /system/jobs/{id}/run`、`POST /system/backfill`。
需要 Write 的接口：`POST /research/backtest`、`POST /market/plan/{id}/simulate-plan`、`POST|PATCH|DELETE /portfolio/plans*`、`POST|DELETE /portfolio/transactions*`、`GET /portfolio/plans/{id}/snapshot`。

调用示例：

```bash
curl -H "X-Admin-Token: $ADMIN_TOKEN" -X POST http://127.0.0.1:8787/api/v1/system/providers/test-all
```

CORS 允许的方法为 `GET/POST/PATCH/DELETE/OPTIONS`，允许的请求头包含 `Authorization`、`Content-Type`、`X-Request-ID`、`X-Admin-Token`；`allow_credentials=False`。生产环境 `CORS_ORIGINS` 含 `*` 时会被自动剔除并回退为 `http://{HOST}:{PORT}`。

## 其他防护

| 措施 | 实现位置 |
| --- | --- |
| 统一错误结构、不返回堆栈 | `main.py` 的 `AppError` 与兜底 `Exception` 处理器（500 固定为 `internal_error`） |
| 安全响应头 | `X-Content-Type-Options: nosniff`、`X-Frame-Options: SAMEORIGIN`、`Referrer-Policy: no-referrer`、`Cache-Control: no-store` |
| 密钥不入日志 | `logging.scrub()` 对敏感键名替换为 `***REDACTED***` |
| 接口不返回密钥 | `GET /system/info` 明确只返回非敏感字段，并附 `note` 说明；配置中心 `GET /system/settings` 对 `sensitive` 项只回 `has_value` + 掩码（`abc************xyz`），**明文只写不读** |
| 生产关闭交互文档 | `docs_url=None when is_production`，`/redoc` 始终 `None` |
| 反向代理层限制 | Nginx 配置中 `/api/v1/system/` 段按 IP 白名单限制（见「24 · 安装部署手册」） |

## 密钥轮换与保管建议

1. `.env` 只在本机保存，代码库只提交 `.env.example`（占位值）；
2. 轮换 `ADMIN_TOKEN` 可在后台「系统设置 → 管理接口令牌」改，**立即生效无需重启**（`SettingsStore.apply_to_settings()` 会写回 `settings` 单例）；注意：改完当前浏览器里已保存的旧令牌会失效，需在页面上重填；
3. 第三方 Key 轮换后可用 `python scripts/btcctl.py probe` 验证，失败源会被自动停用并记 `provider.auto_disable`；也可直接在后台「系统设置 → 数据源密钥」覆盖保存；
4. 备份包含明文 `.env`，`backups/` 目录权限应与 `.env` 同级对待；
5. **后台保存的密钥明文存在 `app_settings` 表里**，因此 `data/btc.db` 与备份包必须按「含密钥」的权限级别保管（见下方局限）。

## 已知局限 / 注意事项

- `ADMIN_TOKEN` 是唯一的管理员凭据；`SECRET_KEY` 只用于**备份包 HMAC 签名**（`scripts/backup.py`），不参与接口鉴权。仍是默认占位值时，备份脚本会如实写 `signature_strength: none`，不假装有效防护。
- `require_admin` / `require_write_permission` 在**生产环境**用 `secrets.compare_digest` 与 `ADMIN_TOKEN` 常量时间比对；**开发环境（`APP_ENV≠production`）直接放行**，因此部署到公网前必须确认 `APP_ENV=production` 且改过 `ADMIN_TOKEN`。
- 没有用户体系、登录会话、CSRF 防护与 API 速率限制；限流仅作用于出站 Provider 请求（`RATE_LIMIT_DEFAULT_QPS`）。
- 前端是否带 `X-Admin-Token` 取决于 `sessionStorage` 里有没有令牌（`/admin` 与 `/settings` 页可填，键名 `btc_admin_token`）。**没填时生产环境下的管理/写操作会被拒绝**，且令牌只活在当前标签页。
- **后台配置中心把密钥明文写进 `app_settings` 表**：换来的是「不用改 .env、不用重启」，代价是数据库文件与备份包现在等同于密钥库。目前未做字段级加密（`SQLite` 本身也没加密），能读 `data/btc.db` 的人就能拿到全部数据源 Key 与 SMTP 密码。若部署在多人可访问的环境，至少应把 `data/` 与 `backups/` 目录权限收紧到仅运行用户可读。
- `.env` 以明文存放，`/system/info` 虽不返回密钥，但备份包会原样复制 `.env*`。
- 未强制 HTTPS；Nginx 配置里的 TLS 段是注释示例，启用需自行申请证书。
- SQLite 数据库文件本身没有加密，拥有文件读权限即可读取全部历史与资金计划数据。
