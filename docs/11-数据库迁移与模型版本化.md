# 11 数据库迁移与模型版本化

一句话定位：升级版本时不重建数据库（那会丢掉所有历史），而是增量补列；同时把「模型版本」与「数据版本」一起入库，保证任何结论都能复现。

## 建表

```python
async def init_db(engine=None):
    async with eng.begin() as conn:
        await conn.run_sync(Base.metadata.create_all)
    await ensure_columns(eng)
```

`create_all` 只创建**不存在**的表，不会动已有表。

## 增量补列（不重建库）

`ensure_columns()` 解决「模型里加了新列、旧库里还没有」的问题：

1. 读取现有列：SQLite 用 `PRAGMA table_info(...)`，PostgreSQL 查 `information_schema.columns`。
2. 与 `Base.metadata.sorted_tables` 中的列做差集。
3. 缺失的列执行 `ALTER TABLE ADD COLUMN`；SQLite 下新增列**一律允许 NULL**，避免影响已有行。
4. 表还不存在时跳过（交给 `create_all`）。

**这是长期运行场景的关键**：升级版本不会要求用户重建数据库，历史数据全部保留。

## 主键与跨库兼容

```python
PK_BIGINT = BigInteger().with_variant(Integer, "sqlite")
```

SQLite 下退化为 `INTEGER`，PostgreSQL 下用 `BIGINT`，同一套模型两种库都能跑。

## TimescaleDB（可选，生产推荐）

```python
HYPERTABLES = [("candles", "ts"), ("market_prices", "observation_time"), ("indicator_values", "ts")]
```

`enable_timescaledb()` 把这三张时序表转为 hypertable。**失败安全**：没有扩展时直接跳过，不影响启动。

## 模型版本化

### `model_versions` 表

| 字段 | 含义 |
| --- | --- |
| `code` | 模型唯一代码 |
| `kind` | `cycle` / `valuation` / `risk` / `forecast` / `strategy` |
| `params` | 参数 JSON |
| `dev_period` / `test_period` | 开发区间与测试区间 |
| `metrics` | 样本外表现 |
| `active` | 是否为当前启用版本 |
| `notes` | 说明 |

### `model_weights` 表

记录每个模型的因子权重与理由（`model_code` / `factor` / `weight` / `rationale`），权重调整可追溯。

### 数据版本

回测结果绑定 `data_version`（历史 K 线范围）与 `model_version`，例如 `"{count}bars_{start_ts}_{end_ts}"`。这样同一条结论在任何时候都能定位到「当时用的数据和模型」。

## 智能监测的规则版本化

`alert_rule_versions` 表在每次修改规则时写入一份完整快照（含条件树）。用户可以在页面上看到「这条规则改过什么、什么时候改的」——删除规则时也会保留历史事件。
