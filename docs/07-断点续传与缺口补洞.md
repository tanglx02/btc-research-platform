# 07 · 断点续传与缺口补洞

本文描述历史数据抓取如何做到「中断后从断点继续」、以及本地缺口如何被发现与补齐。
所有结论均来自源码，行号以当前代码为准。

## 0. 设计铁律

| 原则 | 代码出处 | 说明 |
|---|---|---|
| 分批拉取，每批成功立即写断点 | `backend/app/collectors/base.py:5` | 崩溃后从断点继续，绝不从头重来 |
| 支持暂停 / 继续 / 重试 / 跳过 / 重新同步 | `backend/app/collectors/base.py:6` | 由 `status` 字段表达 |
| 写库前做合理性校验，脏数据不能覆盖正确数据 | `backend/app/collectors/base.py:7` | 见 `market_collector.py:267` |
| 抓一次，永久保存在自己的数据库 | `backend/app/collectors/market_collector.py:5` | 以后看历史只读本地 |
| 无覆盖的窗口如实记录，绝不用假数据填补 | `backend/app/collectors/market_collector.py:171-173`、`223` | `uncovered_windows` |

## 2. 三个方法：`get` / `save` / `reset`

全部实现在 `BaseCollector`（`backend/app/collectors/base.py:35-117`）。

| 方法 | 行号 | 行为要点 |
|---|---|---|
| `get_checkpoint()` | 35-62 | 查不到行时返回 `exists=False` + `cursor_ts=0` + `status=idle` 的**内存默认值**，不写库 |

### 2.1 `save_checkpoint` 的关键细节

| 参数 | 行号 | 作用 |
|---|---|---|
| `cursor_ts` | 101 | `int(cursor_ts) if rewind else max(row.cursor_ts, int(cursor_ts))` —— 默认单调递增 |
| `cursor_date` | 102-103 | **仅当传入真值时才更新**，传 `None` 不会清空旧值 |

| `provider` | 106-107 | 仅当传入非空字符串时覆盖 |
| `error` | 108 | 无条件覆盖（成功路径传 `None`，即清空错误） |
| `extra` | 109-110 | 与旧值做浅合并 `{**old, **new}`，不删除旧键 |
| `updated_at` | 111 | 显式写 `datetime.now(timezone.utc)` |

首行插入时（`base.py:88-98`）`total_rows` 被初始化为 `max(0, rows_delta)`。

## 3. 为什么 `reset` 必须回退（`rewind=True`）

源码自带说明（`base.py:76-81`）：

> 默认 cursor 单调递增（`max`），防止乱序回写把进度倒退；
> 但 `rewind=True` 时允许回退 —— 重新同步（reset）必须真的能清零，
> 否则 `backfill --reset` 看起来成功、实际还是从旧断点继续。

配套的验收注释在 `backend/tests/test_checkpoint_resume.py:11-12`：
「重新同步（reset）必须真的能清零，不能因为实现里写了 max() 而清不掉」。

若不传 `rewind`，`base.py:101` 的 `max(row.cursor_ts, 0)` 会保留旧游标，
于是「重新同步」变成一次空转：接口返回成功，实际一根新数据都没重新抓。
这是典型的「看起来成功但没做事」，与本项目的数据可靠性原则冲突，因此 `rewind` 是必需的。

**必须如实说明的两个残留行为：**

| 现象 | 原因 | 影响 |
|---|---|---|
| `reset` 后 `cursor_date` 仍是旧值 | `base.py:102` 只在真值时更新，而 `reset_checkpoint` 传 `cursor_date=None`（`base.py:115`） | 仅展示/排查信息，不影响续传正确性（续传只看 `cursor_ts`） |
| `reset` 后 `total_rows` 不清零 | `rows_delta=0`，`base.py:105` 是累加而非赋值 | `total_rows` 是「累计写入次数」，不是「当前库里有几行」 |

## 4. 中断后续传：`MarketCollector.backfill`

入口：`backend/app/collectors/market_collector.py:133-224`。

### 4.1 执行流程

| 步骤 | 行号 | 说明 |
|---|---|---|
| 1. 可选 reset | 141-142 | `reset=True` → `reset_checkpoint()` |
| 2. 读断点 | 144-145 | `cursor = int(checkpoint.get("cursor_ts") or 0)` |
| 3. 计算起点 | 147-150 | 无断点用 `BACKFILL_START_DATE`；有断点用 `max(cursor - step, 起点)`，**故意留 1 根重叠防边界缺失** |
| 4. 循环分批 | 162-163 | `batch_end = min(cursor_dt + timedelta(days=batch_days), end)`，`batch_days` 来自 `BACKFILL_BATCH_DAYS`（`market_collector.py:59`） |
| 5. 抓取入库 | 166-168 | `_fetch_and_store(symbol, start_ms, end_ms)` |
| 6. 每批成功后写断点 | 206-211 | `cursor_ts=batch_end`，`rows_delta=rows` |
| 7. 收尾 | 213-216 | `status="done"`，`extra={"uncovered_windows": uncovered[-50:]}` |

`step` 由周期决定（`INTERVAL_SECONDS`，`market_collector.py:30-34`），
`limit` 按窗口跨度动态计算并封顶 1500（`market_collector.py:248-249`）。

### 4.2 中断后的去重机制

断点续传本身**不依赖**任何外部去重表，靠三层保证：

| 层 | 机制 | 出处 |
|---|---|---|
| 重叠窗口 | 续传起点回退 1 根（`cursor - step`），保证边界桶被重新抓一次 | `market_collector.py:150` |
| 唯一约束 | `candles` 表 `UniqueConstraint("symbol","interval","ts","source_id")` | `models.py:190` |
| 幂等写入 | `upsert_candles` 走 `on_conflict_do_update`，重复写入是更新而非报错 | `repo.py:34-57` |

即：即使重叠抓取导致同一根 K 线被提交两次，结果也是同一行被更新，不会撞唯一约束、不会产生重复行。
（幂等实现的完整说明见 `08-存储层Raw与Normalized及幂等写入.md`。）

### 4.3 中断时的断点保留

| 异常类型 | 行号 | 处理 |
|---|---|---|
| `AllProvidersFailedError` 且判定为「真的有故障」 | 175-194 | `save_checkpoint(cursor_ts=cursor_dt, status="failed", error=...)`，返回 `stopped_at` + `reason="all_providers_failed"` |
| 其他异常 | 195-203 | 同样写 `status="failed"` 与 `stopped_at` |
| 未被捕获的崩溃 / Ctrl+C | — | 上一个成功批次已写库（`market_collector.py:206-211`），下次从那里继续 |

CLI 侧对 `KeyboardInterrupt` 的提示：`scripts/btcctl.py:437-439`
「已中断。断点已保存，重新执行同一命令可继续。」

## 6. 哪些窗口会被如实记为「所有数据源均无数据」

这是本文最重要的一节：**没有数据就是没有数据，不允许插值、不允许用相邻 K 线填充。**

### 6.1 两种计入 `uncovered` 的情形

| 情形 | 判定 | 行号 |
|---|---|---|
| 抓取成功但返回 0 行 | `rows == 0` | `market_collector.py:170-174` |
| 全部 Provider 失败，但失败原因全部属于「源本身没有」 | `_all_empty(exc) == True` | `market_collector.py:175-179` |

两种情形都执行 `uncovered.append(window)` 并打日志
`collect.backfill_no_coverage`，然后**继续往前走**，不中断整个回填。

### 6.2 `_all_empty` 的判定标准

`market_collector.py:226-243`。必须**同时**满足：

1. 每次尝试的 `failure_type` 属于下列集合之一，或（`ok=False` 且无 `failure_type`）：

| failure_type | 含义 |
|---|---|
| `empty_data` | 数据源明确没有该窗口数据 |
| `data_format_error` | 返回格式变化（厂商改版） |
| `not_configured` | 没配 Key |
| `circuit_open` | 熔断中 |
| `range_unsupported` | 该交易所不支持按区间拉历史 |
| `provider_unsupported` | Provider 不支持该能力 |

2. 至少有一次尝试的 `failure_type == "empty_data"`（第 243 行的 `any(...)`）。

设计意图（注释在 `market_collector.py:171-172`、181）：
区分「确实没有」与「出错了」。前者记为无覆盖并继续，后者保留断点等待重试 —— 后者才是断点续传真正要覆盖的场景。

### 6.3 无覆盖窗口如何被看到

| 出口 | 位置 | 形式 |
|---|---|---|
| 接口返回值 | `market_collector.py:222` | `uncovered_windows` 列表 |
| 断点 `extra` | `market_collector.py:215` | 仅保留最后 50 个窗口 |
| CLI 打印 | `scripts/btcctl.py:91-97` | 最多列出 20 个，超出提示「还有 N 个窗口」 |
| 文案 | `market_collector.py:223` | 「标记为无覆盖的时间窗口代表所有数据源都没有该区间数据，系统不会用假数据填补。」 |

## 7. 自动补洞：`GapRepairCollector`

`backend/app/collectors/market_collector.py:325-410`。

### 7.1 如何扫描本地缺口

`find_gaps()`（`market_collector.py:341-352`）：

1. 取出该 `symbol + interval` 的全部 `Candle.ts`；
2. 按 `ts // step * step` **归一化到桶**（第 348 行）；
3. 从 `min` 到 `max` 逐个桶遍历，缺失的桶即为缺口（第 352 行）；
4. 若没有任何本地数据，返回空列表（第 349-350 行）—— 无历史时无法定义「缺口」。

注意：缺口只在**已有数据的最小值与最大值之间**查找，
本地覆盖区间之外的空白不属于「缺口」，而属于「尚未回填」。

### 7.2 如何逐个补齐

`repair()`（`market_collector.py:354-407`）：

| 步骤 | 行号 | 说明 |
|---|---|---|
| 取缺口 | 355 | `find_gaps()` |
| 无缺口直接完成 | 356-358 | 写 `status="done"` 返回 |
| 截断处理量 | 360 | `targets = gaps[:max_gaps]`，`max_gaps` 默认 **40** |
| 逐个窗口取数 | 363-374 | `start_ms = gap_ts*1000`，`end_ms = (gap_ts+step)*1000`，`limit=5` |
| 入库 | 394-397 | `upsert_candles` |
| 失败登记 | 398-401 | 返回空行或 `AllProvidersFailedError` → 计入 `failed` |
| 写断点 | 403-406 | `status = "done" if not failed else "failed"`，`extra={"failed_gaps": failed[:20]}` |

**「主源 → 备用源」由谁完成**：`GapRepairCollector` 自己**不遍历** Provider，
它调用 `self.router.fetch(...)`（`market_collector.py:367`），
由 `ResilientRouter.fetch` 按优先级链逐个尝试并在全部失败时抛 `AllProvidersFailedError`
（`backend/app/providers/router.py:113-124` 构造 ordered chain，第 158-165 行切换时登记 failover）。
补洞器把这整条链的结果视为一次尝试。

### 7.3 返回值口径

| 字段 | 含义 | 行号 |
|---|---|---|
| `repaired` | 本轮写入的行数 | 397、407 |
| `remaining` | `len(gaps) - len(targets)`，即因 `max_gaps` 截断而**本轮未处理**的缺口数 | 407 |
| `failed` | 本轮尝试过但仍为空 / 全部失败的缺口数 | 407 |

`remaining` 与 `failed` 语义不同：前者是「还没轮到」，后者是「试过了但没有」。

### 7.4 补洞与回填的行为差异（如实记录）

| 差异点 | `backfill` / `_fetch_and_store` | `GapRepairCollector.repair` |
|---|---|---|
| 价格合理性校验 | 有，`sanity_check_price(c.close, reference)`（`market_collector.py:267`） | **无**，直接使用 Provider 返回值 |
| OHLC 自洽修正 | 有，`high = max(high, max(open, close))`、low 同理（`market_collector.py:277-278`） | **无**，直接写 `c.high` / `c.low` |
| 原始响应留档 | 有，`insert_raw`（`market_collector.py:295`） | **无** |
| 单批规模 | `BACKFILL_BATCH_DAYS`（默认 500 天） | 每窗口 1 根，最多 40 个窗口 |
